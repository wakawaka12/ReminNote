## 二、所有后续阶段的共同执行规则

### 2.1 窗口与提交规则

1. 每个独立模块使用独立 Git worktree；总成窗口负责契约入口、依赖锁定、迁移集成、顺序合并、本地门禁和报告汇总。
2. 独立窗口统一使用 `gpt-5.6-luna`、`max` thinking（即 `lunamax`）；窗口必须在提示中写明允许修改的路径和禁止越界的路径。
3. 独立窗口只能本地 commit，不能自行 push、merge、rebase、tag 或发布；提交说明使用中文，并附 Slice、文件范围、实际构建/测试证据、人工步骤、失败判定和剩余风险。
4. 总成窗口一次只集成一个公共契约或数据库迁移；集成后立即运行相应构建/测试，避免多个未验证公共变化叠加。
5. `ReminNote.sln`、`Directory.Build.props`、`Directory.Packages.props`、所有 `packages.lock.json`、EF migration/model snapshot、根脚本、公共 `App.xaml.cs`、`MainWindow.*` 和根级活文档属于总成串行区域；独立窗口不得并行修改。
6. 任何会改变产品方向、数据模型含义、业务写入者、IPC 身份隔离、迁移失败处理、凭据或备份安全语义的变化，必须先停止编码并追加决策记录；不能用实现细节掩盖契约变化。
7. 开发/测试只能使用显式仓库根目录和隔离数据库。不得读取真实 Token、生产数据库或生产配置；不得把临时测试数据写回正式 `.devdata`。

### 2.2 统一交付门禁

每个阶段的 Slice 都必须提供：

- 实现范围和明确不做的范围；
- 文件所有权和依赖的提交哈希；

阶段集成顺序固定为：**契约冻结 → Core/持久化基础 → 应用服务/Agent → 客户端迁移 → UI/通道 → 失败与恢复测试 → 用户验收 → 阶段报告**。公共契约和 migration 不能与依赖它们的 UI 窗口同时进入总成。

## 三、P2.5：Bootstrap + Agent + IPC + Single Writer

### 3.1 目标和不可违反的边界

P2.5 是架构迁移，不是功能扩张。目标是在 Reminder 开发前将 P2 的本地双宿主写入迁移为长期架构：

- Agent 是唯一业务写入者；Main、Widget 不再直接写 SQLite；
- Main 通过 `Command -> Named Pipe -> Agent` 发出业务命令，使用只读查询或安全读模型；
- Bootstrap 只负责启动、激活、有限重启和安全模式，不承载业务逻辑、不直接操作业务数据库；
- SQLite 启用 WAL，读写边界和进程生命周期必须经过验证；
- 每个成功业务事务在同一事务中产生全局 revision 和 durable Change Journal entry；
- 客户端维护 `LastSeenRevision`，支持 `GET CHANGES SINCE X`，revision 缺口时可回退完整只读刷新；
- 命令必须具备幂等语义，超时、重连、重复 Request 不得重复创建 Task、结果或 History；
- 首版 IPC 使用可审计 JSON，不提前引入二进制协议或通用插件系统；
- IPC 必须包含 `ProtocolVersion`、`RequestId`、超时、重连、当前 Windows 用户隔离和稳定错误码；
- P2 本地 Semaphore 写门只能在切换前作为旧实现存在。任何可运行 checkpoint 都不能同时暴露两个合法业务写入路径。

Widget 的最终宿主组合必须在 P2.5-00 记录：无论 Widget UI 与 Agent 是同进程组合还是通过 IPC 访问，SQLite 的业务写入都只能发生在 Agent 所有的 application path，不能由 Widget 自己持有第二个合法 writer。

### 3.3 P2.5 的安全切换顺序

必须按以下顺序切换，不能让“旧 direct write”和“新 Agent write”同时成为正式入口：

```text
P2.5-00 契约冻结
    ↓
协议/Journal/Agent/transport 在隔离测试中完成
    ↓
Main 与 Widget 客户端适配器完成，但未形成双 writer 的可运行发布点
    ↓
单一 cutover：Agent 接管业务 application service，Main/Widget 移除 direct write 注册和调用
    ↓
断管道、超时、重复 Request、revision 缺口、Agent 重启和权限负测
    ↓
P2.5 阶段验收
```

测试 fake 可以在独立窗口使用，但不能把 fake 当成生产 writer。若切换需要短暂兼容旧数据库 schema，必须通过真实 migration 和回滚/失败策略说明，不得靠删除数据库解决。

### 3.4 P2.5 验收标准

- 两个客户端同时发起创建、结果、改期和排序命令时，只有 Agent 写入，结果和 History 不重复、不丢失；
- 同一个 `RequestId` 重试不会重复产生业务事实，超时后再次查询能得到确定结果；
- Agent 进程重启后，Main/Widget 可以恢复连接、按 revision 增量刷新，revision 缺口可完整刷新；
- 断管道、无权限用户、错误协议版本、过期 ExpectedRevision、Agent 崩溃和重复启动均有稳定反馈；
- `WAL`、journal、revision、command dedup 同步提交/失败回滚有自动化证据；
- 静态审查确认 Main/Widget/Bootstrap 没有生产业务直写入口，Bootstrap 没有数据库操作；
- 正常桌面人工验收确认单实例、Agent 重启、双宿主操作、数据保留和失败后 UI 状态；
- 不引入 ReminderRule、Scheduler、Toast 业务、Anime 网络或 Sync。

## 四、P2.75：最低迁移与数据安全门禁

### 4.1 目标和边界

P2.75 位于 P2.5 与 P3 之间，目标是让第一个 P3 日常 Alpha 能安全处理真实个人数据。固定流程为：

```text
Backup → Migration → Verify → Startup
```

必须满足：迁移前创建安全备份；原始数据库保留；迁移后执行基本验证；失败时停止正常写入/启动；向用户暴露清晰恢复入口；不对唯一原文件做破坏性原地修复。

P2.75 不做完整 Recovery Center、复杂修复器、全量备份保留管理、数据库加密或智能数据合并；这些属于后续范围。

### 4.3 P2.75 验收标准

- 用带已有 P1 Task 的副本执行 forward migration，旧 Task、结果和 History 保留；
- 迁移前存在可读备份，备份不包含 Token/凭据，原库不会被覆盖；
- 模拟 schema 错误、锁失败、磁盘/复制失败和验证失败时，应用进入明确失败/恢复状态，不继续普通业务写入；
- 正常 migration 后核对 migration history、表结构、外键、SQLite integrity 和关键行数；
- 第二次启动/迁移幂等，不能重复导入 History 或重复生成业务事实；
- 用户能看到下一步恢复路径，但不会被要求删除唯一数据库；
- 自动化、CLI、隔离 clone 和正常桌面人工证据分开记录；
- P2.75 不提前引入 Reminder 调度或 Sync。

## 五、P3：生产 Reminder loop / 首个日常 Alpha

### 5.1 P3 目标与冻结边界

P3 是第一个面向真实日常使用和有限朋友测试的 Alpha。Agent 继续是唯一业务 writer；Task 计划时间和 Reminder 通知时间必须保持独立。P3 需要实现 Reminder 的真实事实、调度和通知通道，但不把 Toast 本身当作 Reminder 系统。

P3 明确不做：自动更新器、LAN/self-hosted Sync、Anime 网络、复杂数据集合并、通用插件系统。P3 是单设备/local-first 阶段。

固定模型：

```text
ReminderRule       = 业务真相，说明为什么/何时提醒
ReminderSchedule   = 可重建的派生执行状态
ReminderInstance   = 实际触发及生命周期历史事实
```

已触发的历史 Instance 不重写；规则或 Task 时间变化使旧 pending Schedule 失效并产生新 revision；Snooze 产生带 `SNOOZE` cause 的派生 schedule，不改原 Rule；TaskInstance 完成只取消未来 pending/snooze，不删除历史。

### 5.3 P3 并行关系

契约冻结后，以下工作可以并行：

- Reminder domain/schema 与 Notification abstraction；
- scheduler 的纯计算/重建测试与 channel adapter；
- Toast、Tray、Widget alert 三个通道；
- Main Drawer、Widget compact panel 和 Export/Restore 工具；
- 优先级/Quiet Hours 的纯规则测试与 UI 状态展示。

以下工作必须串行：

- Reminder migration 与 model snapshot；
- Agent scheduler 对持久化规则/计划/实例的最终接线；
- Task 完成对未来 Schedule 的取消边界；
- 通知故障/睡眠恢复的最终状态机；
- P3 Alpha 稳定性门禁和用户实际使用结论。

### 5.4 P3 验收标准

- `ANYTIME` 默认不凭空生成时钟提醒；`TIME` 使用全局提前量；`RANGE` 可有开始前、开始或结束复盘提醒，且不改变 Task 计划形状；
- Rule、Schedule、Instance 分层可查询；改期/规则变更产生新 revision，历史 Instance 不变；
- Scheduler 只等待最近需要的唤醒，能够处理已到期批次、Agent 重启和睡眠恢复；
- 同一命令重复提交不重复产生 Reminder/History；Task 完成后未来 pending 与 Snooze 不再触发，但已触发历史保留；
- Toast 被禁用时，Tray/Widget/健康状态仍能表达事实，不把“通道不可用”伪装成“没有触发”；
- Snooze 不改原 Rule，Quiet Hours 只影响通知呈现，不冻结 Task/调度事实；
- Drawer 生命周期 `UNREAD → READ → RESOLVED` 正确，动作通过 Agent 命令边界执行；
- 结构化导出、受控恢复和手动升级可验证，升级不能要求删除数据库；
- 用户实际使用后没有已知 BLOCKER/MAJOR Reminder 正确性问题；Agent、重启、睡眠恢复、迁移安全和通知通道失败均有证据。

P3 Stability Gate 不设固定“等待 7 天/30 天”规则，依据真实使用和稳定性证据决定是否进入 P4。

## 六、推荐的并行派发顺序

### 6.1 当前立即执行

1. 总成窗口完成本文件及 P2 Pending 状态的本地文档检查点。
2. 派发一个独立的 P2.5-00 窗口，只产出契约/Slice/威胁模型提案，不直接改 Main/Widget 业务代码，不改变 P2 写入路径。
3. 总成审核 P2.5-00 后，按 P2.5-01/02/03/04 的所有权分别派发；契约未冻结前不派发依赖它的生产切换代码。
4. P2.5-08 通过后再派发 P2.75；P2.75-00 通过后再派发 P2.75 实现窗口。
5. P2.75-04 通过后才进入 P3-00；P3-00 是新的串行契约冻结点。

### 6.2 并行窗口的安全上限

建议每个契约层最多 3 个实现窗口同时运行，避免总成审查和 lock/migration 冲突失控：

```text
契约冻结：1 个总成窗口
基础实现：最多 3 个独立窗口
客户端/通道：可按 Main、Widget、Toast、Tray、Export 分开并行
公共迁移/切换/阶段验收：1 个总成窗口串行
```

并行不是同时改同一文件。每个窗口必须使用独立 worktree；若发现需要修改别的窗口所有权文件，停止并在报告中提出集成请求。

## 七、阶段完成定义与禁止事项

阶段完成必须同时满足：代码范围完成、构建/测试通过、无新增未解释警告、架构边界有效、数据/安全规则有效、文档和 Slice 更新、人工步骤可执行、用户关键行为已验证、剩余风险已记录。

禁止事项：

- 不因为 P2 午夜暂时无法测试而伪造通过或修改系统时钟；
- 不把 P2 的本地 Semaphore 当成 P2.5 Single Writer；
- 不把单实例激活 pipe 当成 Agent 业务 IPC；
- 不在 P2.5 迁移期间保留两个正式业务 writer；
- 不把 Reminder、WAL、Change Journal、Sync 或 Anime 网络提前塞回 P2；
- 不把 CLI、harness、独立静态审查或条件性 UI smoke 写成用户正常桌面签字；
- 不在迁移/恢复失败时删除原数据库或要求用户“删库重来”；
- 不在 P3 为了赶 Alpha 提前加入网络同步、自动更新器或通用插件系统。
