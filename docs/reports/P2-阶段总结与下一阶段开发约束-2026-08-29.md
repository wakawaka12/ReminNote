## 3. P2 的目标与实际交付

在 Agent 迁移前，把真实 Task/SQLite 接入 TODAY 和 Widget，形成可以日常使用的本地 Task loop：

`创建 → 查询/分组 → 修改/重排 → 记录结果 → 重启保留 → Widget 同步显示`。

P2 不是 Reminder 系统，也不是 Agent/IPC 迁移。它的职责是先把 Task 业务事实、结果和必要历史
做成可靠的本地闭环，并为后续单写者迁移保留清晰边界。

### 3.3 P2 已形成的用户可用闭环

P2 当前已经实现以下闭环：

- 创建 Task：支持 `ANYTIME`、`TIME`、`RANGE`，使用确定性 Parser；
- 查询 Today：使用系统时区和持久化工作日边界，显示今天及未完成历史计划；
- 分组和状态：支持计划时段、`OPEN`、`COMPLETED`、`OVERDUE`、`AWAITING RESULT`、`NEEDS REVIEW`；
- 完成和结果：`DONE` 记录 `COMPLETED`，RANGE 明确记录 `COMPLETED`、`PARTIAL` 或 `MISSED`；
- 结果语义：`RecordedAt` 只表示记录动作时间，不能把结果记录时间伪装成计划时间；
- 计划修改：无结果 Task 可以按规则改期，已有结果 Task 不得改时间；
- 同组排序：只允许同一计划日期、同一 Today 分组内调整，不借排序伪造改期；
- 继续关系：只有 `PARTIAL RANGE` 可以继续，继续 Task 使用新的 UUID v7，并指向原 Task；
- 历史：结果、计划变化、排序变化、继续关系和 P1 导入快照均写入 `task_history`；
- Widget：读取同一 TaskWorkspace，允许规定范围内的写入，禁止自行改期；
- 重启：本地 Task、结果和历史保留；
- 失败保护：Parser 失败、写门超时、写入失败或刷新失败不得静默覆盖原数据或清空原列表。

## 4. P2 冻结的产品和数据规则

这些规则是下一阶段必须继续遵守的输入，不得因为实现方便而重新解释。

### 4.1 时间、工作日和 Today

- Task 的时间形状只有 `ANYTIME`、`TIME`、`RANGE`。
- 默认时区是系统时区，测试必须可以注入固定时区和时钟。
- 默认工作日边界为 `00:00`，配置以分钟持久化在单例 `app_settings` 中。
- 跨午夜 RANGE 归属开始日期；结束前仍是活动任务，结束后才进入待复盘语义。
- 今天显示今天计划和未完成历史计划；未来日期不进入 Today 活动列表。
- 结束 RANGE 没有结果时进入 `AWAITING RESULT`/`NEEDS REVIEW`，不得自动写入 `MISSED`。

### 4.2 Parser、结果和历史

- Quick Add Parser 必须是纯函数、确定性、可测试的边界；不支持的标签/优先级保留语法必须拒绝，
  不得静默丢弃或把整段输入误当成标题。
- 结果可以覆盖式保存当前状态，但每次记录都追加不可变历史快照。
- 计划修改、排序和继续关系也必须保留必要的历史事实。
- 已有结果 Task 禁止修改计划日期/时间；稳定错误码为 `task.time_spec.changed_after_result`。
- `PARTIAL` 只能用于 RANGE；继续动作不改变原 Task、原计划或原结果。

### 4.3 写入边界与数据安全

- Main 和 Widget 不得直接访问 DbContext、EF entity、SQL 或 SQLite 文件；必须经过 application/query service。
- P2 的本机完整读-改-写由命名 `Semaphore(1, 1)` 写门保护；这不是 P2.5 的 Agent 单写者。
- 写门超时必须稳定失败且保留原数据。
- P2 migration 只扩展 Task history、设置、排序和继续关系，不创建 Reminder/Anime/Sync 表。
- 开发升级必须通过 forward migration，不得以删除数据库代替升级。
- 数据安全、migration、IPC、加密和更新器变更必须经过额外审查。

## 6. 下一阶段路线

主计划明确的顺序是：

`P2 一审 → P2.5 架构迁移 → P2.75 最小数据安全 → P3 Reminder 日常 Alpha`。

### 6.1 P2.5：Bootstrap + Agent + IPC + Single Writer

P2.5 是架构迁移 Slice，不是功能扩张 Slice。目标是在生产 Reminder 之前完成长期进程架构。

范围包括：

- Bootstrap 进程；
- Agent 进程；
- Main App 激活和生命周期；
- Named Pipe 协议；
- Single Writer；
- 只读查询层；
- SQLite WAL；
- Change Journal；
- 全局 revision 和恢复；
- 幂等命令模型；
- 现有 P2 Task 操作全部经过 Agent 路径。

P2.5 的硬性迁移规则：

> 任一可运行检查点只能存在一条合法业务写入路径。

一旦 Agent 接管写入，Main App 的业务直写必须移除；不能出现“Agent 写入”和“Main 直写”同时作为
合法路径的过渡版本。P2.5 不实现新的 Reminder 产品功能、完整 Reminder 系统或 Anime 网络功能。

### 6.2 P2.75：最低数据安全

P2.75 的目标是让 P3 日常 Alpha 足够安全地承载真实个人数据。

范围包括：

- migration 安全备份；
- migration 前后验证；
- 升级失败时停止普通写入；
- 保留原始数据库；
- 最小恢复入口；
- 可测试的升级路径。

不在 P2.75 追求完整 Recovery Center、备份保留管理器、复杂修复 UI 或完整加密系统。

### 6.3 P3：Production Reminder loop

P3 才开始生产 Reminder：`ReminderRule`、`ReminderSchedule`、`ReminderInstance`、调度器、持久化、
Toast、Tray、Widget 提醒、Reminder Drawer/Center、Quiet Hours、睡眠/重启恢复、通知健康、导出和受控恢复。

P3 仍是 single-device/local-first，不实现 LAN Sync、self-hosted Sync、复杂数据集合并、通用插件系统
或 Anime 网络。Agent 在 P3 继续作为唯一业务写入者。

只有 P2.5 和 P2.75 通过各自门禁后，才允许派发 P3。届时可考虑以下并行流：

## 8. 下一阶段所有独立窗口的统一执行纪律

### 8.1 窗口和模型

- 每个独立窗口使用自己的 Git worktree；禁止多个窗口写同一工作目录。
- 独立窗口统一使用 `gpt-5.6-luna`，推理强度使用 `max`；总成窗口只负责契约、分派、监工、集成和门禁。
- 子窗口不得自行 push、merge、rebase、force-push、tag 或 release。
- 子窗口不得修改 `reviews/`、`second-review/`，不得读取生产数据库、Token 或生产配置。

### 8.2 文件所有权

以下内容由总成窗口串行处理，独立窗口只能提出修改请求：

- `ReminNote.sln`、`Directory.Build.props`、`Directory.Packages.props` 和各项目 lock 文件；
- App/Bootstrap/MainWindow 公共生命周期；
- 共享导航壳、Design System、根脚本和 `.github/workflows/`；
- migration、数据库公共 schema、公共 IPC/Revision 契约；
- 根级活文档、阶段总报告和最终集成记录。

功能窗口必须严格遵守对应 Slice 的路径所有权；需要新依赖、公共接口或共享资源时，只提交请求和
最小设计，不在自己的窗口中擅自修改公共文件。

### 8.3 每个模块的交付内容

每个大模块必须有一个可审查的本地中文 commit，并同时提供：

1. 变更范围和未变更范围；
2. 实际 Release 构建/测试命令及完整结果；
3. 人工验收步骤、预期结果和失败判定；
4. 数据、并发、恢复和安全风险；
5. 对其他窗口的依赖和集成顺序；

## 10. 失败判定与停止条件

- 一审要求与当前实现不一致但尚未有用户决定；
- 出现两个合法业务写入者；
- Main/Widget 绕过 Agent 或 application/query boundary 直写数据库；
- 重复命令重复创建 Task、结果、历史或 Reminder；
- IPC、迁移、崩溃或恢复失败造成数据丢失、静默覆盖或无审计变化；

- 无法确认当前代码、数据库或测试结果属于哪个 commit/工作区。
