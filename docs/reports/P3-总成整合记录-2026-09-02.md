## 依赖审查与开放 seam

1. P3-01 的 `ApplyReminderConfigurations()` 仍是显式 opt-in，尚未接入 `ReminNoteDbContext`、迁移或 model snapshot；这是 P3-03/P3-09 的持久化接线项。
2. Domain、Calculation、Notifications 各自保留契约枚举，名称/值不能直接强转。尤其 P3-02 的 planner reason 与 Domain 的 `ScheduleStateReason` 需要显式 adapter。
3. P3-04 的 `NotificationDeliveryAttempt`（带 correlation/idempotency）与 P3-01 的 `ReminderDeliveryAttempt`（核心历史字段）需要在 Agent 单写事务中明确映射，不能把 channel 失败写成核心 Instance 失败。
4. P3-08 仍是窄 DTO；Schedule 的 purpose/priority/pinned snapshot 与实际 persistence shape、Rule/target 存在性、Candidate migration/marker/fingerprint 需要 P3-09 决定，当前没有真实数据库接线。
5. P3-03、P3-05、P3-06、P3-09 尚无本地完成窗口；当前测试只证明纯契约、策略、计算、通知 seam 和受控 restore plan，不证明真实进程、Named Pipe、WPF、系统通知、sleep/wake 或用户 sign-off。

后续依赖顺序保持 P3-00 第 13 节 DAG：P3-01 + P3-02 + P3-04 先进入 Agent scheduler/due transaction（P3-03），再由 Agent/UI 接入真实 channel（P3-05/P3-06），P3-07/P3-08 作为策略与 Candidate adapter 输入，最后由 P3-09 串行执行 gate、真实进程和桌面人工验收。
