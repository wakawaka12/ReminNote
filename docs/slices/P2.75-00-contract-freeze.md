| 项目 | 值 |
|---|---|
| 文档版本 | `RN-P275-SAFETY-1.0.0` |

| 输入基线 | `3ab342b`（`codex/p0-integration` / `origin/main` 当前指向） |
| 前置阶段 | P2.5-00 至 P2.5-04；P2.5 Agent/Storage/Transport 契约与实现输入 |
| 当前状态 | **冻结候选，待总成审查并记录接受后生效** |

本文是 P2.75-00 的安全语义冻结，不是 P2.75-01/02/03 的实现报告，也不是用户数据
迁移已经成功的证明。总成接受本文以前，后续窗口只能做明确标记为 non-runnable 的隔离
准备；不能把本文的提交、fake、CLI smoke 或自动化测试写成生产迁移通过。

## 1. 目标、效力和边界

P2.75 位于 P2.5 与 P3 daily-use Alpha 之间。它只建立最小、可恢复、可审计的迁移门禁：

```text
Resolve → Quiesce/Lock → Backup → Stage → Forward Migration → Verify → Atomic Promote → Startup
```

目标是：

- 在任何 schema migration 前得到一个可独立读取的安全副本；
- 迁移只在候选库上进行，活动库在备份和候选验证成功前保持原样；
- 备份、迁移、验证、切换或状态记录任一步失败，应用进入明确的 fail-closed 状态；
- 用户可以查看失败状态并选择一个已验证的安全副本恢复，不被要求删除唯一数据库；
- 正常升级、第二次启动、失败重启和人工回滚都有可执行的验收断言。

本文不授权：

- 修改 `src/`、EF migration、model snapshot、Solution、包锁或生产启动代码；
- 完整 Recovery Center、复杂修复器、逐行编辑、智能合并或跨库导入；
- 全量自动备份保留/轮转管理；
- 数据库加密、自定义密码学、自动更新器或二进制下载/签名链路；
- Reminder、Scheduler、Sync、Anime 网络或任何 P3 业务功能；
- 在迁移失败时恢复 P2 Main/Widget direct writer。

P2 的真实跨午夜人工 Pending 仍独立存在；P2.75-00 不覆盖、不替代、不关闭它。

## 2. 基线事实与后续接入点

本窗口先以实际仓库状态而不是旧计划中的假设作为实现输入：

1. `ReminNoteDatabase.DevelopmentRelativePath` 仍是仓库相对的
   `.devdata/reminnote.sqlite`；P2.5 的 profile resolver 已要求显式 root、canonical path、
   当前 Windows user 和 `ProfileScope`。
2. 当前 P2.5 Agent 的 `OpenStoreAsync` 使用 `ReadWriteCreate` 打开活动数据库，随后调用
   `Database.MigrateAsync`，再初始化 P2.5 storage store。这是 P2.75-02 必须包在安全门禁
   后面的现有接入点，不是本文宣称已经安全。
3. 当前 Bootstrap 只通过 control health 等待 Agent，尚未提供本文定义的迁移失败状态和
   恢复命令。Bootstrap 仍不得打开业务库；迁移/验证/恢复的数据库操作归 Agent recovery
   actor。
4. 当前基线的已知 EF history 顺序为：

   ```text
   20260828025922_InitialTaskSchema
   20260828120000_P2TaskLoop
   20260828130000_P2ContinuationDeleteBoundary
   20260831090000_P25StorageConsistency
   ```

   后续目标 migration 必须明确写入兼容矩阵；不能把 AppVersion、SchemaVersion、
   IpcProtocolVersion 混为一个版本号。
5. 当前 P2.5 storage 表为 `revision_state`、`change_journal`、`command_receipt`，并与
   P2 的 `tasks`、`task_history`、`app_settings` 同库。P2.75 不改变这些业务语义，也不在
   本 Slice 预建 Reminder/Anime/Sync 表。

## 3. 术语、身份和 canonical 路径

### 3.1 逻辑对象

| 名称 | 定义 |
|---|---|
| Active DB | 当前 profile 对外提供业务数据的 `reminnote.sqlite`；失败时不得被未验证候选覆盖 |
| Safety Backup | 迁移前从 Active DB 得到的、可独立打开且带 manifest/hash 的 SQLite 文件 |
| Candidate DB | 从同一份安全快照创建、允许执行 forward migration 的隔离文件 |
| RunId | 每次迁移/恢复尝试新生成的规范小写 UUID；不使用 Task ID、RequestId 或用户文本 |
| Source Schema | 迁移前 `__EFMigrationsHistory` 的有序 migration ID 集合 |
| Target Schema | 当前应用声明支持的有序目标 migration ID 集合 |
| Recovery Required | 需要用户/维护者明确选择状态查看、重试或恢复；禁止普通业务写入的状态 |

`ProfileScope`、当前 user SID 和 canonical DB path 继续遵循 P2.5-00 契约。备份文件名
不是权限边界；所有文件 ACL 和 Agent 应用层 profile/SID 双检仍必须存在。

### 3.2 profile 目录布局

沿用 P2.5-00 的 root/profile 规则，不读取 cwd、环境变量、注册表或隐式用户目录：

| 对象 | `default` profile | 非 `default` profile |
|---|---|---|
| DataRoot | explicit `--data-root`，或 isolated repo 的 `.devdata` | 同左 |
| ProfileRoot | `DataRoot` | `DataRoot\profiles\<profile>` |
| Active DB | `ProfileRoot\reminnote.sqlite` | `ProfileRoot\reminnote.sqlite` |
| 安全备份 | `ProfileRoot\backups\` | `ProfileRoot\backups\` |
| 失败/候选证据 | `ProfileRoot\recovery\` | `ProfileRoot\recovery\` |
| 状态 marker | `ProfileRoot\runtime\migration-state.json` | `ProfileRoot\runtime\migration-state.json` |

路径要求：

- 必须明确传入且 canonicalize；`--data-root` 与 `--repo-root` 同时出现仍然拒绝；
- 不存在的 profile 目录只能由 Agent/Bootstrap 在 root 校验通过后创建；不得先创建未知路径；
- root、profile、backup、recovery、runtime 目录均不得通过 reparse/symlink 越出 DataRoot；
- 不接受 UNC/远程路径；不因大小写、`.`、`..` 或尾部分隔符制造第二个 profile；
- 文件和 marker 只授予当前 user 的最小权限，保留 OS 必需的 SYSTEM 访问，但不授予
  `Everyone`、`Users` 或管理员组业务读取/写入权限；
- 本窗口和所有隔离验证**绝不读取或写入** `D:\Anime\.devdata\reminnote.sqlite`，也不复制
  该路径的 `-wal`、`-shm` 或 journal sidecar。

### 3.3 测试根目录

真实用户库、仓库工作树的 `.devdata` 和测试 fixture 必须分开。P2.75 验证使用每次新建的
临时目录，例如：

```powershell
$testRoot = Join-Path ([IO.Path]::GetTempPath()) ('ReminNote-P275-00-' + [Guid]::NewGuid().ToString('N'))
$testDataRoot = Join-Path $testRoot 'data'
New-Item -ItemType Directory -Path $testDataRoot -Force | Out-Null
```

测试必须把绝对 `testDataRoot`/profile 写入证据；测试结束只清理由本次测试创建并已核对
绝对路径的临时目录。不得把测试 profile 复制回任何正式 `.devdata`。

## 4. 不可违反的安全不变量

1. **先备份，再迁移。** Active DB 存在时，安全备份创建并通过独立可读性验证以前，不能
   对 Active DB 或 Candidate DB 执行 migration。
2. **迁移不在唯一原文件上进行。** Candidate DB 是唯一允许被 migration 修改的文件；
   Active DB 在 candidate 验证成功前必须保持原始字节/sidecar 组合和原路径。
3. **验证不是启动。** migration、integrity、foreign key、schema/history、关键行数和
   备份 hash 未通过前，Agent 不报告 ready，Bootstrap 不启动正常 Main/Widget 业务路径。
4. **失败 fail closed。** 任一失败进入稳定状态并停止普通 mutation；可以提供最后安全的
   只读状态/快照，但不能调用 P2 application service、P2 Semaphore 或 direct writer。
5. **原始数据可追溯。** 安全备份、失败 candidate、原 Active DB（如发生切换准备）和
   manifest 不得被正常流程静默删除、覆盖或轮转。
6. **切换原子且成套。** 只有验证后的 Candidate 才能原子 promote；数据库与其 WAL/SHM/
   journal generation 不能跨代拼接。无法保证成套切换时判定 promote failure。
7. **恢复也先验证。** 恢复必须把选中的备份放入新的 Candidate，先只读验证，再原子 promote；
   不执行 EF `Down`、不编辑唯一原库、不“删库重来”。
8. **只有 Agent 触碰业务库。** Bootstrap 只做生命周期、marker/status 和启动协调；Main/
   Widget 只有只读/业务 pipe client，不能成为迁移、恢复或回滚 writer。
9. **不把异常当事实。** UI、日志、manifest 只使用稳定 failure code 和 bounded metadata；
   不写入 Task 标题、Notes、附件、Token、Authorization header、同步密钥或恢复密钥。

## 5. 备份契约

### 5.1 备份前置条件

迁移 actor 必须按以下顺序执行：

1. 解析并显示/记录 canonical ProfileRoot、Active DB、目标 schema 和 RunId；路径失败立即停止。
2. 取得 profile migration lock；不能无限等待。锁失败直接返回 `migration.locked`，不迁移、
   不覆盖备份、不启动普通写入。
3. 停止或 quiesce Bootstrap、Agent、Main、Widget 及其他本 profile 业务 writer；没有
   “大概没有写入”的假设。任何未知 writable handle 都判 gate 失败。
4. 读取 Active DB 的 source fingerprint（至少 schema history、文件长度、SHA-256/等价稳定
   指纹和 sidecar 状态）。如果在备份后到 promote 前发现 source 变化，返回
   `migration.source_changed`，不尝试合并。
5. Active DB 存在时创建 Safety Backup；Active DB 不存在时只允许创建新的 Candidate，
   manifest 明确记录 `source=empty`，不能把空库伪装成已有数据的备份。

### 5.2 复制一致性

备份必须是一个不依赖源文件 sidecar 的独立 SQLite 文件。实现可选择经过审查的 SQLite
backup API、等价的事务一致快照或在完全 quiesced 后的安全复制，但必须满足：

- 复制期间不能有业务 writer；
- 已提交 WAL 内容必须进入独立备份；
- 不允许只 `File.Copy` 正在写入的主文件后声称备份成功；
- 不把 `reminnote.sqlite-wal`、`reminnote.sqlite-shm` 或 rollback journal 单独当作备份；
- 备份关闭后可在没有源 sidecar 的情况下以 read-only 打开；
- 备份文件写入临时同目录文件，flush/write-through 后再原子 rename；同名目标不能覆盖；
- 备份和 manifest 的 ACL 继承 ProfileRoot 的最小权限。

### 5.3 命名、manifest 和保留

安全备份位于 `ProfileRoot\backups\`，文件名不包含标题、用户名、Task ID 或自由文本：

```text
migration-{fromSchemaToken}-{toSchemaToken}-{yyyyMMddTHHmmssfffZ}-{runId}.sqlite
migration-{fromSchemaToken}-{toSchemaToken}-{yyyyMMddTHHmmssfffZ}-{runId}.json
```

`fromSchemaToken`/`toSchemaToken` 只允许来自已验证 migration ID 的安全字符；空库使用
`empty`。如果最终文件名超过 Windows 安全长度、发生碰撞或目录不可写，返回稳定错误，
不能覆盖旧备份。

manifest 至少包含以下 bounded metadata：

| 字段 | 规则 |
|---|---|
| `contractVersion` | `RN-P275-SAFETY-1.0.0` |
| `runId` | 规范小写 UUID |
| `profileScope` | 当前 profile 的公开 scope，不接受客户端自报值 |
| `sourceSchema` / `targetSchema` | 有序 migration ID 或 `empty` |
| `createdAtUtc` | UTC、ISO 8601、不可用本地时间替代 |
| `artifact` | backup 目录内的相对文件名，不接受绝对路径 |
| `byteLength` | 备份文件实际长度 |
| `sha256` | 备份文件完整内容的 64 位小写 hex |
| `sourceFingerprint` | promote 前用于检测 Active DB 是否变化的 bounded 指纹 |
| `result` | `verified`；未验证/部分复制不能生成成功 manifest |

manifest 不包含绝对数据库路径、Task 内容、History 内容、原始异常文本、Token、凭据、
Authorization header 或任何可恢复密钥。备份/失败证据在 P2.75 不做自动 retention；正常
流程不得自动删除安全备份或失败证据。容量管理属于后续契约。

### 5.4 备份成功判定

只有同时满足以下条件才能写入 `result=verified` 并进入下一阶段：

- 文件存在、长度大于零且 SQLite header/打开检查通过；
- read-only 打开不依赖 Active DB 的 sidecar；
- `PRAGMA integrity_check` 返回精确的 `ok`；
- `PRAGMA foreign_key_check` 返回零行；
- manifest hash 与重新读取的文件 hash 一致；
- 关闭所有读句柄后再次读取 hash 仍一致；
- 备份目标不是 Active DB、Candidate DB 或任一旧 backup 的路径；
- 原 Active DB 与 sidecar 仍存在且 source fingerprint 未在本阶段改变。

任何一步失败均为 `BACKUP_FAILED`，部分文件移入本 RunId 的失败证据目录或保留为未验证
artifact，但不得被后续流程当作安全备份使用。

## 6. 原库保护、Candidate 和原子切换

### 6.1 Candidate 规则

Candidate 放在：

```text
ProfileRoot\recovery\staging\<runId>\candidate.sqlite
```

Candidate 必须从刚刚验证的 Safety Backup（或 `source=empty` 的新文件）产生。所有 EF
forward migration、schema DDL 和 P2.5 `EnsureProfile` 类初始化只能针对 Candidate 执行。
生产 migration runner 禁止对 Active DB 调用 `ReadWriteCreate` 后直接 `Database.Migrate`。

Candidate 失败时保留在：

```text
ProfileRoot\recovery\failed\<runId>\
```

目录中，带 manifest/state 关联；不把失败 candidate 移回 Active DB 路径。

### 6.2 Active DB 的硬保护

以下动作无论“为了修复”还是“为了重试”都禁止：

- `EnsureDeleted`、`EnsureCreated`、`DROP TABLE`/`DROP DATABASE` 或清空重建；
- EF `Down` migration 作为线上/用户回滚路径；
- 在 Active DB 上直接做 destructive repair、truncate、重写唯一原文件；
- 删除 Active DB 后再启动新空库；
- 将 P2 `CrossProcessTaskWriteGate`、Main/Widget `TaskWorkspace` 或备用 application service
  作为 Agent 不可用时的 fallback；
- 用未验证 backup、另一 profile 或任意用户提供的裸 SQLite 路径覆盖 Active DB；
- 删除或重命名失败证据后把状态伪装成 `READY`。

在 Candidate 验证成功前，Active DB 的绝对路径、内容、文件长度和 sidecar generation 必须
保持不变。若 promote 需要把旧文件移出活动路径，旧 generation 必须先以成套、可读、带
RunId 的 original artifact 保存在 `recovery\history\<runId>\`；该 artifact 和 Safety
Backup 均是回滚入口，任何一个保存/校验失败都不能 promote。

### 6.3 Atomic promote

promote 必须：

1. 再次确认所有业务 writer 已停止、migration lock 仍由当前 RunId 持有；
2. 确认 Active DB fingerprint 与备份前一致；变化返回 `migration.source_changed`；
3. 关闭 Candidate 的所有连接，处理其 sidecar，使 Candidate 是完整的一代文件；
4. 在同一 ProfileRoot/卷内，以平台支持的原子 replace/rename 机制切换整代文件；
5. 切换后重新打开 Active DB 做完整 post-promote verify；
6. 只有 post-promote verify 成功才写 `READY` 并让 Agent 报告 `ready=true,writable=true`。

切换中断、结果无法判定或新旧文件无法对应时，进入 `PROMOTION_UNKNOWN`，不得猜测哪一
代已经生效；保持所有文件和状态，转入 Recovery Required。

## 7. 失败状态、marker 和业务写入门禁

### 7.1 状态集合

`ProfileRoot\runtime\migration-state.json` 是不依赖业务 DB 的状态源。状态名和 failure code
是机器可读契约；UI 文案只是稳定映射，不能取代状态字段。

| 状态 | `ready` | `writable` | 含义与下一步 |
|---|---:|---:|---|
| `READY` | true | true | 目标 schema、备份/切换后的验证和 P2.5 health 均通过 |
| `MIGRATION_REQUIRED` | false | false | 发现已知旧 schema；先执行本文流水线 |
| `BACKUP_IN_PROGRESS` | false | false | 备份尚未验证；停止普通启动/写入 |
| `BACKUP_FAILED` | false | false | 未取得可用安全备份；修复磁盘/权限后显式重试 |
| `MIGRATION_IN_PROGRESS` | false | false | Candidate 正在执行 forward migration |
| `MIGRATION_FAILED` | false | false | Candidate migration 失败；Active DB/backup 保留 |
| `VERIFY_IN_PROGRESS` | false | false | post-migration checks 尚未完成 |
| `VERIFY_FAILED` | false | false | Candidate 未通过验证；不得 promote |
| `PROMOTION_IN_PROGRESS` | false | false | 正在做整代原子切换，不能启动客户端 |
| `PROMOTION_UNKNOWN` | false | false | 切换结果不确定；必须人工进入恢复路径 |
| `RECOVERY_REQUIRED` | false | false | 存在失败证据或 marker 不可安全解释；只允许 status/restore |
| `RECOVERY_IN_PROGRESS` | false | false | 用户明确选定 backup 后正在验证恢复 Candidate |
| `RECOVERY_FAILED` | false | false | 恢复 Candidate/切换/验证失败；继续保留原库与备份 |

`READ_ONLY`/`UNAVAILABLE` 是 Main/Widget 对上述非 READY 状态的显示模式，不是绕过状态的
新 writer 状态。即便 Active DB 仍然可以安全读取，客户端也只能显示 stale/readonly；
不能因为备份失败而继续使用旧 P2 写路径。

### 7.2 marker 内容与原子更新

marker 至少保存以下 bounded、非敏感字段：

- `contractVersion`、`state`、`runId`、`profileScope`；
- `sourceSchema`、`targetSchema`、`backupArtifact`（profile 内相对名）；
- `backupSha256`、`candidateArtifact`（相对名，可空）；
- `startedAtUtc`、`updatedAtUtc`、`failureCode`、`retryable`、`nextAction`；
- `lastKnownGoodSchema` 和 `lastAgentInstanceId`（若有）。

marker 最大 8 KiB，不含 Task/History/Notes/附件、绝对路径、原始异常、Token、凭据或恢复密钥。
写入必须是同目录临时文件 + flush/write-through + 原子 replace；不能先删除旧 marker。
marker 目录 ACL 只允许当前 user 的最小权限。marker 缺失、损坏、字段越界或无法原子写入时，
应用选择 `RECOVERY_REQUIRED`/unavailable，而不是默认 `READY`。

### 7.3 稳定 failure code

实现可以记录更细的内部诊断，但对客户端、报告和验收只暴露以下稳定 code：

| Code | 触发 | 是否允许普通写入 |
|---|---|---:|
| `migration.args_invalid` | root/profile 参数歧义或非法 | 否 |
| `migration.path_invalid` | canonical/reparse/ACL/path containment 失败 | 否 |
| `migration.locked` | profile migration lock 无法取得 | 否 |
| `migration.source_invalid` | Active DB 不是可读 SQLite 或 source history 无法读取 | 否 |
| `migration.backup_failed` | 复制、空间、权限、flush 或目标创建失败 | 否 |
| `migration.backup_unreadable` | backup 打开/hash/integrity/FK 验证失败 | 否 |
| `migration.source_changed` | backup 后 Active DB fingerprint 变化 | 否 |
| `migration.incompatible_schema` | 未声明 source/target 兼容或发现未知 schema | 否 |
| `migration.apply_failed` | forward migration 在 Candidate 失败 | 否 |
| `migration.verify_failed` | schema/history/关键数据/完整性验证失败 | 否 |
| `migration.integrity_failed` | `integrity_check` 非 `ok` | 否 |
| `migration.foreign_key_failed` | `foreign_key_check` 有结果 | 否 |
| `migration.history_failed` | history 缺失、重复、顺序不符或目标不完整 | 否 |
| `migration.promote_failed` | 原子切换明确失败 | 否 |
| `migration.promote_unknown` | 切换结果无法判定 | 否 |
| `migration.state_unwritable` | 不能安全持久化 failure marker | 否 |
| `migration.recovery_required` | 需要用户选择恢复或兼容版本 | 否 |
| `migration.recovery_backup_invalid` | 选定 backup 不存在、hash 不符或不可验证 | 否 |
| `migration.restore_failed` | 恢复 Candidate/切换/post-verify 失败 | 否 |

UI 的最小信息必须包含：状态、稳定 code、是否允许写入、备份 artifact ID（若已验证）和
下一步 `查看状态 / 显式重试 / 选择安全备份恢复 / 退出`。不能显示“迁移成功”或“肯定未写入”
等与状态矛盾的自由文案；不能要求删除数据库。

### 7.4 状态转换和重启

```text
MIGRATION_REQUIRED
    -> BACKUP_IN_PROGRESS -> MIGRATION_IN_PROGRESS | BACKUP_FAILED
    -> MIGRATION_IN_PROGRESS -> VERIFY_IN_PROGRESS | MIGRATION_FAILED
    -> VERIFY_IN_PROGRESS -> PROMOTION_IN_PROGRESS | VERIFY_FAILED
    -> PROMOTION_IN_PROGRESS -> READY | PROMOTION_UNKNOWN
    -> READY

任一失败/异常重启 -> RECOVERY_REQUIRED
RECOVERY_REQUIRED -> RECOVERY_IN_PROGRESS -> READY | RECOVERY_FAILED
```

- 每次阶段开始前先写阶段 marker；阶段完成后再写下一阶段；
- Agent crash、机器断电、marker 与文件不一致时，下一次启动不能盲目重复写 Active DB；
  先进入 `RECOVERY_REQUIRED`，通过 artifact/hash/fingerprint 判断并等待显式 status/retry/restore；
- 普通启动最多执行一次完整 migration attempt，不允许失败后无限自动重试；
- `READY` 只能由 post-promote verify 写入，不能由“进程启动了”推导；
- Bootstrap 的 P2.5 watchdog/backoff 仍受其原契约约束，但不能把 migration failure 当作
  Agent healthy，也不能启动 Main/Widget direct fallback。

## 8. Verify 验收清单

后续 P2.75-01/02/03/04 必须逐项记录 `PASS`/`FAIL`/`N/A`，并附 commit、隔离 root、
profile、绝对 artifact path、RunId、PID、退出码和 failure output。下面是契约，不是本窗口
已经执行的结果。

### 8.1 Preflight/backup

| ID | 检查 | 通过断言 | 失败即停止 |
|---|---|---|---|
| V01 | root/profile | 只有一个明确 root；canonical path 在当前 user/profile 下 | 读 cwd/env/未知目录或跨 root |
| V02 | writer quiesce | 无 Bootstrap/Agent/Main/Widget/其他 writable handle | 任何竞争 writer |
| V03 | migration lock | 当前 RunId 独占 lock，等待有上限 | lock 失败仍继续 |
| V04 | source inventory | Active DB、sidecar、schema history、source fingerprint 可记录 | 猜测 schema/吞掉异常 |
| V05 | backup ordering | Active DB 存在时 backup 验证完成后才创建 migration Candidate | 未备份即 `Migrate` |
| V06 | backup standalone | backup 不依赖源 sidecar，read-only 可打开 | 仅复制主文件/无法读取 |
| V07 | backup integrity | `integrity_check=ok`、FK 零行、hash 稳定 | 部分/损坏 artifact 被当成功 |
| V08 | secret boundary | 只复制允许的 SQLite 数据；无 Token/凭据/secret sidecar/原始异常 | 递归复制 DataRoot 或泄密 |

### 8.2 Candidate/post-migration

| ID | 检查 | 通过断言 | 失败即停止 |
|---|---|---|---|
| V09 | candidate isolation | migration 只写 `recovery\staging\<RunId>`，Active DB 未变化 | Active DB 被写/删除/覆盖 |
| V10 | forward-only | 只执行已批准的 forward migration；不执行 `Down`/破坏性修复 | 未知或 destructive path |
| V11 | migration history | history 按预期有序、无重复，target 完整 | history 缺行/乱序/伪造 |
| V12 | schema allow-list | 目标表、列、约束、索引与已批准 manifest 一致；不出现未来未授权表 | schema 漂移/引入 Reminder/Sync |
| V13 | SQLite health | `integrity_check=ok`、`foreign_key_check` 零行、WAL/foreign_keys 符合 P2.5 | 任一健康检查失败 |
| V14 | legacy facts | P1/P2/P2.5 旧 Task、Result、History、Settings、revision/journal/receipt 的 ID/行数按迁移映射保留 | 丢行、重复、改写历史事实 |
| V15 | candidate artifact | Candidate 关闭后 hash/size 稳定，可独立只读打开 | sidecar 跨代或 hash 变化 |
| V16 | source unchanged | promote 前 Active DB fingerprint 与备份前一致 | 未知 writer/源文件变化 |

### 8.3 Promote/startup/recovery

| ID | 检查 | 通过断言 | 失败即停止 |
|---|---|---|---|
| V17 | atomic promote | 只切换经过 V09-V16 的 Candidate，旧 generation/backup 均可恢复 | 半切换、孤儿 sidecar、旧库丢失 |
| V18 | ready gate | post-promote verify 完成后才 `ready=true,writable=true` | 启动成功即 ready |
| V19 | failed startup | 任一失败时 Main/Widget 不写库；可显示 readonly/unavailable/status | P2 fallback 或普通 mutation |
| V20 | second startup | 第二次启动/迁移不新增 migration history、不重复导入 History/业务事实 | 重复事实或重复 migration |
| V21 | status entry | `--recovery-status` 可读 bounded marker，不打开/返回业务内容 | status 命令读写业务库 |
| V22 | explicit restore | 只恢复 hash 通过的 backup；先 Candidate verify，再 atomic promote | 裸路径覆盖/直接复制到 Active |
| V23 | restore failure | 恢复失败保留 Active、backup、candidate、marker，继续 blocked | 删除证据或假装恢复成功 |
| V24 | evidence separation | contract/unit、CLI/clone、real-process、normal-desktop、user sign-off 分开 | fake/CLI 冒充用户签字 |

### 8.4 建议的只读 SQL 断言

实现可用 Microsoft.Data.Sqlite 或等价只读工具执行；命令本身不是权限绕过：

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
PRAGMA journal_mode;
PRAGMA foreign_keys;
SELECT migration_id FROM __EFMigrationsHistory ORDER BY rowid;
SELECT name, type FROM sqlite_master
  WHERE name NOT LIKE 'sqlite_%' ORDER BY type, name;
```

`integrity_check` 必须是精确 `ok`，`foreign_key_check` 必须零行。历史和 schema 结果按
approved manifest 比较，不把包含用户内容的行直接写入报告。关键行数/ID 可以在测试进程
内比较，报告只保留数量、hash 或“保持不变”的断言。

## 9. 故障注入矩阵

| 故障点 | 期望状态/code | Active DB | 允许恢复动作 |
|---|---|---|---|
| root/profile 歧义或 reparse escape | `RECOVERY_REQUIRED` / `migration.path_invalid` | 不触碰 | 修正明确路径后重试 |
| lock 被另一 writer 持有 | `MIGRATION_REQUIRED` / `migration.locked` | 不触碰 | 停止竞争进程后显式重试 |
| backup 目录无权限/空间不足 | `BACKUP_FAILED` / `migration.backup_failed` | 不触碰 | 修复目标条件后重试 |
| backup hash/read/integrity 失败 | `BACKUP_FAILED` / `migration.backup_unreadable` | 不触碰 | 重新生成新 RunId；旧 artifact 保留 |
| source 在 backup 后变化 | `RECOVERY_REQUIRED` / `migration.source_changed` | 不覆盖 | 重新 quiesce 并重新备份 |
| schema/source 不兼容 | `RECOVERY_REQUIRED` / `migration.incompatible_schema` | 不触碰 | 选择兼容 binary/新契约；不强迁移 |
| Candidate forward migration 抛错 | `MIGRATION_FAILED` / `migration.apply_failed` | 原样保留 | 查看状态、重试或恢复 Safety Backup |
| integrity/FK/history/关键行数失败 | `VERIFY_FAILED` 对应 verify code | 原样保留 | 丢弃/保留 Candidate 供诊断；不可 promote |
| promote 明确失败 | `RECOVERY_REQUIRED` / `migration.promote_failed` | 不假设变化 | 先核对 generation，再 status/restore |
| promote 结果不确定/进程崩溃 | `PROMOTION_UNKNOWN` / `migration.promote_unknown` | 不写 | 停止全部进程，人工选择恢复 |
| marker 无法原子写入 | `RECOVERY_REQUIRED` / `migration.state_unwritable` | 不写 | 修复 runtime 权限；不默认 READY |
| restore Candidate 失败 | `RECOVERY_FAILED` / `migration.restore_failed` | 保留 | 选择另一已验证 backup 或维护者介入 |

任何故障都不能通过删除 Active DB、创建空库、固定时间、换 profile、跳过 verify 或恢复
direct writer 来“清除”。

## 10. 最小恢复入口契约

P2.75 不做完整 Recovery Center，只冻结一个可脚本化、可人工确认的最小入口。入口是
Bootstrap/本地 CLI 的用户体验，但任何业务 DB 操作必须由 Agent 的 recovery actor 完成。
当前代码还没有这些 option；P2.75-02/03 必须按本文接入，直到接入完成不得把命令写成已可用。

### 10.1 状态查看

命令形状：

```powershell
ReminNote.Bootstrap.exe --data-root <isolated-data-root> --profile <profile> --recovery-status
```

`--repo-root <isolated-clone>` 可作为等价输入，但必须派生到该 clone 的隔离 `.devdata`，
不能指向正式库。`--recovery-status`：

- 只读 runtime marker、manifest 和 bounded 文件元数据；
- 不打开业务 SQLite，不执行 migration，不发送 Task/History/receipt 内容；
- 返回 state、stable code、RunId、source/target schema、backup artifact ID、hash 状态、
  `ready/writable/recoveryRequired` 和下一步；
- marker 可读时即使状态是失败也能返回状态；marker 不可读时返回非零并保持 blocked；
- 不把原始异常、绝对路径、用户内容或 secret 返回给未授权 control caller。

### 10.2 明确选择安全备份恢复

命令形状：

```powershell
ReminNote.Bootstrap.exe --data-root <isolated-data-root> --profile <profile> `
  --recovery-restore <backup-artifact-id> --confirm
```

规则：

1. artifact ID 只能解析到该 profile 的 `backups` 目录；不接受任意绝对路径或 `..`；
2. `--confirm` 是用户明确选择，不允许普通启动自动恢复；
3. Bootstrap 先停止/确认所有本 profile 进程，随后只负责启动 recovery actor；Bootstrap
   本身不能打开 DB、复制 DB 或执行 `Migrate`；
4. Agent recovery actor 验证 manifest/hash/SQLite integrity/FK/schema compatibility，把备份
   复制到新的 recovery Candidate，验证成功后才 atomic promote；
5. 当前 Active DB、失败 Candidate、Safety Backup 和状态 marker 均按 RunId 保留；失败仍为
   `RECOVERY_FAILED`/`RECOVERY_REQUIRED`；
6. 恢复成功后重新执行 startup verify，只有 Agent 报 `READY` 才开放业务写；不自动执行
   未经验证的业务命令，不重放未知 command receipt；
7. 恢复入口不支持逐行修复、两库 merge、删除历史、改写 Reminder 或导入外部数据库。

UI 最小可等价为一个失败对话框/状态页，必须能“查看状态、退出、选择已验证备份恢复、
显式重试”；不需要完整列表、搜索、智能建议或高级修复布局。

## 11. 升级、幂等和回滚契约

### 11.1 正常 forward upgrade

1. 使用明确 AppVersion/SchemaVersion/target migration 组合；未知 source/target 立即阻止。
2. 按第 5 节创建并验证 Safety Backup；没有可读 backup 不进入 migration。
3. 从 backup 生成 Candidate，仅执行已审查的 forward migration；保持 P2/P2.5 事实。
4. 运行第 8 节 verify；通过后 atomic promote，再运行 post-promote verify。
5. Agent 取得 P2.5 storage health/unique writer ready 后，Bootstrap 才允许 Main/Widget 正常启动。
6. 在同一 target schema 上第二次启动只做健康确认，不重复导入 Task/History，不重复生成
   业务事实、revision、journal 或 receipt；不需要为了“看起来有动作”再生成 migration。

P2.75 不要求每次已是 target schema 的正常启动都生成新 backup；但每一次真正的 migration
attempt 都必须有唯一 RunId 和对应 Safety Backup/manifest，旧 backup 不覆盖。

### 11.2 回滚定义

P2.75 的“回滚”只指从已验证的迁移前 Safety Backup 恢复到新 Candidate，再验证并 atomic
promote；不指执行 EF `Down`，也不指直接覆盖唯一 Active DB。

回滚前置条件：

- 停止 Bootstrap、Agent、Main、Widget 和其他 writer；
- 记录当前 AppVersion、SchemaVersion、migration history、Active fingerprint 和所有 PID；
- 核对 Safety Backup manifest/hash/schema compatibility；
- 使用与 backup schema 兼容的旧 binary/完整 release 组合；不能只替换一个 exe/DLL；
- 恢复 Candidate 通过 integrity/FK/history/关键数据验证后才切换；
- 失败时保留当前 Active、original generation、backup、Candidate 和 marker，不删除任何一个。

P2.75 不实现自动 updater、版本目录切换、下载、签名验证或一键降级。用户/维护者必须
明确选择已知兼容的旧应用组合；发现旧 binary 与新 Agent/新 schema 共存时，停止所有业务
写并报告 `migration.incompatible_schema` 或 `migration.promote_unknown`。

### 11.3 crash/restart 语义

| 崩溃位置 | 下一次启动 |
|---|---|
| backup 前/中 | Active DB 不应变化；marker 进入 recovery/status，未验证 partial 不可使用 |
| backup 完成、migration 前 | backup 可供显式重试/恢复；普通写仍禁用 |
| Candidate migration/verify 中 | Active DB 仍为旧代；保留 Candidate，进入 status/retry/restore |
| promote 前 | Active DB 仍为旧代；重新核对 source/backup 后才可显式重试 |
| promote 中/结果未知 | `PROMOTION_UNKNOWN`；禁止自动再次 promote，先人工 status/restore |
| promote 后、post-verify 前 | 不得报告 ready；按新旧 generation/hash 进入 recovery，不能猜测成功 |
| post-verify/READY 后 | 正常重启只做幂等 health check，不重复业务导入 |

- 没有 push、merge、rebase、tag 或 release。若项目要求检查点，只能是本地提交。

### 13.2 后续正常路径人工验收

以下是实现完成后的用户验收稿，不是本窗口已执行结果。

**环境**

1. 使用批准 commit 创建隔离 clone，并生成新的临时 `data-root`/profile；记录 Windows user/SID、
   AppVersion、目标 SchemaVersion、ProfileScope、Active DB 绝对路径和初始 hash。
2. 准备带已有 P1 Task、Result/History 和 P2.5 revision/journal/receipt 的可恢复 seed；确认
   seed 不来自 `D:\Anime\.devdata\reminnote.sqlite`。
3. 关闭所有 profile 进程；确认 `reviews/`、`second-review/` 只读无 diff。

**正常升级**

1. 使用明确的 `--data-root` + `--profile` 启动迁移 gate；观察先出现 backup artifact/manifest，
   再出现 Candidate migration 和 verify 状态。
2. 验证 Safety Backup 可读、hash 稳定、不含 secret sidecar，Active DB 在 promote 前未变化。
3. verify 通过后观察 Agent `ready=true,writable=true`，再启动 Main/Widget；写入一条测试
   command 后检查只产生预期的一条业务事实和一条 revision/journal/receipt。
4. 完全退出并第二次启动；核对 migration history、Task/History/receipt/revision 行数不重复，
   旧 Task/Result/History 仍保留。

**失败和恢复**

1. 分别注入 backup 目录权限/空间失败、profile lock 失败、非法/损坏 source、migration
   apply failure、integrity/FK/history verify failure、marker 写失败和 promote unknown。
2. 每次失败都确认 Active DB、已验证 backup 和失败证据仍存在；Main/Widget 只显示
   readonly/unavailable，不能创建或修改 Task。
3. 使用 `--recovery-status` 查看 bounded state/code；不应需要打开业务库或删除文件。
4. 明确选择一个 hash 通过的 backup 执行 `--recovery-restore ... --confirm`；确认先生成
   Candidate、通过 verify、再切换，恢复失败仍 blocked。
5. 恢复后重新启动，只有 post-verify/Agent health 通过才恢复写入；核对旧数据和 History。

**失败判定**

- 迁移前没有可读 Safety Backup；
- Active DB 在 Candidate verify 前被写、删、覆盖或与错误 sidecar 拼接；
- 未 ready/恢复失败仍有普通业务写入或 P2 direct fallback；
- 任一 `integrity_check`、FK、schema/history、关键行数或 hash 检查被跳过/吞错；
- 第二次启动重复导入 History/业务事实或生成重复 revision/journal/receipt；
- status/restore 接口暴露用户内容、secret、原始异常或接受任意路径；
- marker 无法解释却被当成 READY，promote unknown 被自动猜测；
- 要求用户删除唯一数据库，或把 fake/CLI/自动化写成正常桌面用户签字；
- 引入 Recovery Center、加密、智能合并、自动更新、Reminder/Sync 等越界内容。
