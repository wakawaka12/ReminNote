## 1. 复核结论

结论：**有条件通过**。

这里的“有条件通过”表示：提案的总体架构方向可以作为总成的冻结输入，且
没有发现会改变 ReminNote 当前产品范围的新方向；但提案仍有若干会影响跨窗口
实现一致性、故障语义和 cutover 证明的契约缺口。在总成明确记录这些契约之前，
不得把本复核写成“契约已冻结”，不得据此让多个窗口各自发明协议或 schema，
不得开始会同时保留两个合法业务 writer 的生产实现。

已确认一致的主线如下：

1. Agent 是唯一业务 writer；Main 采用
   Command → Named Pipe → Agent；Widget 不形成第二 writer。
2. Bootstrap 只负责启动、激活、恢复和 safe mode，不打开业务库，不执行
   业务迁移或业务命令。
3. 当前 Main/Widget 的单实例激活 pipe 仍是 host activation，不是业务 IPC。
4. JSON envelope、ProtocolVersion、RequestId、idempotencyKey、
   ExpectedRevision、timeout/cancel/reconnect 都被纳入候选协议。
5. global revision、Change Journal、GET CHANGES SINCE、WAL、Agent restart
   和 watchdog/safe mode 的方向与主计划一致。
6. Change Journal 被明确限定为变更通知、增量恢复和一致性证明，不是
   Event Sourcing；Reminder、Anime、Sync 不提前进入 P2.5。

仍需冻结的重点是：请求尝试和逻辑请求的 RequestId 语义、hash canonicalization、
receipt 的终态覆盖范围、响应和错误 envelope 的必填字段、framing 的字节序与
资源上限、revision gap 的完整检测、read channel 和 Widget 拓扑、ACL/profile
规范、safe mode UX，以及 cutover 的可重复验收证据。

**未发现新增产品方向问题。** 原提案的七项未决契约确认仍然保留，且下文
补充的协议和验收细化不能被解释成 Reminder、Anime、Sync 或新的 Task 产品功能。

P2 状态不因本复核改变：P2 代码和自动化门禁已经闭环（Release 8/8、0
warning/error、测试 191/191、P0-07 通过），但真实

### 3.1 当前激活 pipe 的专门结论

当前代码只读检查得到的事实是：

- Main 的当前实例互斥和激活通道仍使用
  Local\ReminNote.Windows.Main 与 ReminNote.Windows.Main.Activation，
  消息是 activate；
- Widget 的当前实例互斥和激活通道仍使用
  Local\ReminNote.Widget 与 ReminNote.Widget.Activation，消息也是
  activate；
- 这些当前通道没有 ProfileScope，也没有 Task command、SQL、payload 或
  idempotency 语义；
- 当前 P2 的 Main 和 Widget 仍各自初始化 TaskWorkspace，并通过 P2
  本地 writer gate 直接写业务库，这是 cutover 前的既定状态，不是本复核
  发现的新增实现。

因此，提案没有误把当前 Main/Widget 单实例激活 pipe 当成业务 IPC。提案
§4.1 L175-L192 已明确未来业务 pipe 使用
  ReminNote.Agent.〈ProfileScope〉，且 §8.4 L756-L765 要求激活消息不能改变
业务状态。集成请求是：不要把现有无 profile 的 Activation 名称直接升级成
业务 endpoint；要在总成冻结 ProfileScope、ACL、实例拓扑和 endpoint 命名后，
显式建立业务 pipe，并保留 activation/control 与 business 两种权限边界。

### 3.2 Change Journal 的语义结论

提案 §6.3 L526-L565 明确 journal 只保存变更元数据，不保存完整事件回放
payload，不自动重建任意历史状态，也不是用户可见的 History。这个判断与主
计划的“global revision + durable journal，用于增量同步和恢复”一致。因此
没有把 Change Journal 误写成 Event Sourcing；总成仍需防止后续实现将
journal 当作第二事实源或未来业务事件总线。

## 4. 风险登记

严重级别含义：阻断冻结表示没有明确契约就不应冻结公共接口或派发依赖它的
生产窗口；重大表示可以做隔离性准备，但不能进入最终 runnable checkpoint；
一般表示需补入测试或文档门禁。

### R-ACT-00：现有 Activation endpoint 不能复用为业务 endpoint

- 严重级别：重大。
- 提案证据：§4.1 L175-L192 明确区分 business pipe、当前 Main/Widget
  activation pipe 和 Bootstrap control；§8.4 L756-L765 要求 activation
  payload 不得改变业务状态。
- 复核结论：语义没有冲突，但当前代码的 pipe/mutex 名称未按 profile
  隔离，且当前 Widget 是单实例 P2 形态。若实现窗口把已有
  ReminNote.Windows.Activation 或 ReminNote.Widget.Activation 当成 Agent
  business pipe，会破坏 scope、ACL 和迁移证据。
- 必须冻结：业务 endpoint 的 canonical ProfileScope 派生、control endpoint
  与 business endpoint 的命名、payload 允许字段、权限和兼容期；Activation
  pipe 只能承载激活/控制意图，不能承载 Task、SQL、命令幂等键或业务响应。

### R-REQ-01：RequestId 的 retry 语义自相矛盾

- 严重级别：阻断冻结。
- 提案证据：§4.2 L199-L220 将 RequestId 描述为“一个逻辑请求的关联”
  并要求 retry 复用；§4.3 L258-L259 又说 retry response 使用当前 retry
  requestId；§4.8 L417-L420 再次要求 reconnect 时同一 requestId、
  idempotencyKey 和 hash 保持不变。
- 复核结论：wire attempt correlation 和 logical command identity 尚未
  分开。若客户端复用 RequestId，服务端如何区分连接尝试与同一响应重放未
  定；若每次尝试生成新 RequestId，又与 §4.2、§4.8 冲突。
- 必须冻结：推荐采用“每个 wire attempt 一个 requestId；写命令的
  idempotencyKey 表示稳定逻辑意图；command.status/retry 使用新的
  requestId，但必须复用同一 key 和 payload hash”的模型；若总成选择
  提案另一模型，须给出请求、响应、断线重连的时序图和测试向量，并统一
  全部章节文字。

### R-IDEM-02：幂等 payload hash 的 canonicalization 不可执行

- 严重级别：阻断冻结。
- 提案证据：§4.3 L244-L257 只规定 SHA-256、canonical JSON、UTF-8，
  hash 包含 operation、expectedRevision、payload，排除 requestId、
  clientInstanceId、timeout 和 sentAt。
- 复核结论：没有规定字段排序、数字表示、负零、null/缺省区别、Unicode
  规范化、重复 JSON key、转义形式、未知字段、数组顺序，以及是否包含
  protocol/schema/profile 版本。不同语言实现可能得到不同 hash，无法可靠
  判定“同 key 不同命令”。
- 必须冻结：选择明确的 canonical JSON 规范或写出完整算法；给出至少成功、
  空 payload、Unicode、数字、未知字段和数组的 golden vectors；明确
  idempotencyKey 的 profile 作用域、hash 版本和存储长度。hash 不得包含
  用户敏感文本以外的额外日志输出，也不得被客户端随意改写。

### R-RECEIPT-03：receipt 终态和 no-op/stale 处理不完整

- 严重级别：阻断冻结。
- 提案证据：§6.1 L498-L508 规定 no-op 不增长 revision；§6.2
  L512-L524 说 stale receipt 可选；§6.3 L526-L565 定义 receipt 字段和
  Committed/Rejected/RolledBack；§7.2 L682-L691 规定 receipt 与业务
  事务同提交，但没有覆盖所有结果矩阵。
- 复核结论：如果 no-op、ExpectedRevision mismatch 或 cancelled 不落
  durable receipt，同一 key 后续能否安全 replay 未定义；如果落 receipt，
  response payload、status 和“新 key 重试”规则也未定义。Rollback、
  pre-commit timeout、commit 后 response 丢失、pending/unknown 之间的
  终态需要一张统一表。
- 必须冻结：至少覆盖 changed commit、changed=false durable replay、
  deterministic rejection/stale、事务 rollback、cancel before commit、
  commit-after-timeout、response loss、pending、unknown；定义每种状态的
  key reuse、command.status 结果、CommittedRevision、错误码和 retention。
  建议所有能被重放的业务请求都有受约束的终态 receipt，禁止“半写入但无
  可查询事实”。

### R-ENV-04：response/error envelope 的必填语义不足

- 严重级别：重大。
- 提案证据：§4.2 L199-L220 定义了共同字段以及 ok/replayed；§4.4
  L263-L322 给出响应示例和部分条件语义；§5 L456-L496 给出错误码表。
  §4.3 L244-L251 的“无 idempotency 的操作”列表还没有明确包含
  request.cancel。
- 复核结论：成功、replayed、业务拒绝、协议错误、超时未确认和权限错误
  各自必须返回哪些字段尚未冻结；serverRevision、agentInstanceId、
  requestId、retryable、details 的存在性和敏感字段上限不明确。Bootstrap
  出现在 clientKind 候选中，但 Bootstrap 不得提交业务 command，控制
  endpoint 和业务 envelope 的边界需显式化。
- 必须冻结：success/error 的 schema、所有 response 必填字段、错误对象
  的 machine-readable code/retryable/details、未知字段策略、大小限制、
  敏感信息脱敏，以及 request.cancel 是否允许/如何相关联。错误 message
  不能成为机器契约。

### R-FRAME-05：framing 的字节序、资源上限和连接错误处理未冻结

- 严重级别：重大。
- 提案证据：§4.6 L352-L365 规定 UTF-8 JSON、4-byte unsigned length、
  1 至 1 MiB frame、duplex stream 和建议的 in-flight/timeout 数值。
- 复核结论：4-byte length 的 byte order 未定；“建议 32”、2000/5000
  毫秒、最大 30 秒不是契约；partial read/write、整数溢出、过大 frame
  的分配顺序、event/response interleaving、连接关闭后的 outstanding
  request 终态没有完全定义。
- 必须冻结：字节序（推荐明确写 big-endian 或 little-endian）、frame/
  payload/error/details 的独立上限、in-flight 上限、解析前分配策略、截断/
  非 UTF-8/非法 JSON 的 close 和错误行为、读写/整体 deadline、event 与
  response correlation；把“建议”数值转为可测试配置或明确默认值。

### R-VERSION-06：ProtocolVersion minor negotiation 未定义

- 严重级别：重大。
- 提案证据：§4.2 L199-L203 要求 protocolVersion 1.0；§4.7
  L367-L393 规定 major 不兼容时关闭、minor 兼容但只写了“rules”
  未定义。
- 复核结论：可接受版本区间、未知字段与 feature downgrade、hello response
  的最终版本、服务端拒绝原因和客户端能力声明没有形成可执行协议。
- 必须冻结：major/minor 比较算法、支持范围、hello 成功/失败 envelope、
  feature negotiation、未知字段策略、未 ready 时禁止的操作，以及升级/
  回滚时 receipt 和 journal 的兼容边界。

### R-REV-07：revision gap 检测和分页一致性仍有漏洞

- 严重级别：阻断冻结。
- 提案证据：§6.4 L567-L614 定义 afterRevision、maxRevisions、
  oldest/current 和 gap；§6.5 L616-L636 定义 snapshot revision 和
  LastSeen 更新。
- 复核结论：按 oldestAvailable 推断 gap 不能发现 journal 中间缺行；
  maxRevisions 的 0、负数、极大值和并发写入时的上界没有明确；同一
  transaction 的多条 change 已要求不拆分，但分页算法和
  toInclusive 的原子观察点仍需精确。after=0、first revision=1 的非 gap
  特例、after>current、整数下溢和 journal 损坏必须有测试。
- 必须冻结：journal revision 连续性/完整性检查、事务 revision 批次边界、
  最大 page、并发请求的 snapshot upper bound、gap/ahead/error 规则；
  read model 应用失败时保持旧模型，只有完整对应 snapshot 成功应用后才
  推进 LastSeenRevision。必要时提供带 SnapshotRevision 的同事务 read
  contract，而不是让客户端猜测。

### R-READ-08：read channel 和 profile/data path 未决

- 严重级别：重大。
- 提案证据：§3.1 L124-L141 允许 Main/Widget 读取 WAL 下的 SQLite 或
  Agent model；§15.1 L1137-L1142 将 read channel、ProfileScope 和
  data-root 输入列为未决；§4.1 L175-L192 要求 pipe 按 profile 隔离。
- 复核结论：两条路线的权限、快照 revision、失败时 stale 标记、性能和
  测试证据不同。当前 P2 的 validated root 和直接 TaskWorkspace 不能被
  模糊地沿用到 post-cutover。
- 必须冻结：选定 same-DB readonly 或 Agent unified read model；若 same-DB，
  定义 canonical absolute path、只读/query-only 约束、同一 read transaction
  取得模型与 revision、禁止 schema PRAGMA/Migrate/SaveChanges；若 Agent
  model，定义完整 query response 和 SnapshotRevision。同步冻结
  repo-root、data-root、profile 的优先级和跨进程 canonicalization。

### R-WIDGET-09：Widget topology 与 instance identity 未决

- 严重级别：重大。
- 提案证据：§2.1 L89-L98 把 Widget 写成 N/instance 且默认 independent
  WPF；§8.3 L742-L754 区分相同 WidgetInstanceId 激活和不同 ID 共存；
  §15.1 L1134-L1136 将“独立 exe 还是同进程”列为未决。
- 复核结论：这不构成新的产品方向，但影响 Agent ownership、activation
  scope、pipe name、生命周期和测试。主计划允许 N WidgetInstance，而
  当前 P2 Widget 是单实例激活模型，不能把二者当作已经兼容。
- 必须冻结：independent exe 或 Agent-hosted model、WidgetInstanceId 的
  来源/持久性、相同 ID 的 activate 规则、不同 ID 的并存规则、profile/
  user/instance 对 mutex 和 pipe 的命名，以及 Widget 崩溃时是否影响 Agent。

### R-SAFE-10：watchdog/safe mode 的数值和 UX 未完全冻结

- 严重级别：重大。
- 提案证据：§8.2 L727-L740 提供 10 分钟、最多 3 次、1/2/5 秒 backoff
  等建议，并区分健康 safe mode 与健康检查失败；§15.1 L1149-L1150
  将 safe mode 写权限和 UX 列为未决。
- 复核结论：建议值不是验收契约；marker 的位置、原子更新和清除条件、
  restart 计数窗口、Agent 停止时的 UI 状态、健康 safe mode 的写按钮和
  failed-health readonly 行为尚未具体化。
- 必须冻结：状态机、计数/窗口/backoff、marker ACL 和恢复条件；健康
  safe mode 是否允许核心 Task 写入；失败 safe mode 是否只读；所有状态
  都必须禁止 Main/Widget 直接 fallback、禁止删除业务库，并有用户可理解
  的提示。

### R-CUT-11：cutover 验收目前不足以证明唯一 writer

- 严重级别：阻断冻结。
- 提案证据：§9.1 L769-L786 区分 pre/post writer；§9.2 L788-L817

## 6. 必须由总成冻结的契约清单

在下发 P2.5-01/02/03/04 的最终生产实现任务前，总成应逐项给出决定、版本、
责任人和对应测试证据。以下项目当前均视为“待冻结”：

1. **范围与阶段边界**：P2.5 只做 Agent/lifecycle/pipe/single writer/
   readonly query/WAL/revision/journal/idempotent existing P2 Task；不加入
   Reminder、Anime、Sync、网络、E2EE、updater、new Task time shape 或
   Event Sourcing。
2. **actor/topology**：Bootstrap、一个 Agent、一个 Main、N 个 Widget
   的实际进程关系；Widget 是否 independent exe；每个实例的退出和激活
   规则。
3. **writer/read 权限**：唯一业务 writer 是 Agent；Main/Widget 的具体
   read channel；任何 test fake 只能在测试边界存在；所有 runnable
   checkpoint 只能有一条合法业务写入路径。
4. **ProfileScope/data root**：canonical 输入、hash 算法、repo-root/
   data-root/profile 参数优先级、路径规范化、profile 与当前用户绑定。
5. **endpoint 与 ACL**：Activation/control 与 Agent business pipe 的
   名称、scope、SID ACL、SYSTEM/admin 例外、越权错误和敏感 metadata
   泄露边界；不得复用当前激活 pipe 作为业务 endpoint。
6. **envelope**：request/response/event/error 的必填字段、camelCase、
   JSON UTF-8、unknown field/type 规则、payload 和 error 上限。
7. **ProtocolVersion**：major/minor 协商、hello、feature downgrade、
   ready 前允许的操作、版本不兼容时的稳定错误与关闭行为。
8. **RequestId 与重试**：wire attempt correlation、logical command、
   reconnect、command.status、response loss 的统一语义。
9. **framing/limits**：4-byte length 字节序、frame/request/response/
   details 上限、in-flight 上限、partial read/write、截断、非法 UTF-8、
   read/write/overall timeout 和连接关闭策略。
10. **command/error map**：P2 现有 Task domain operation、每项是否需要
    ExpectedRevision/idempotencyKey、稳定错误码、retryable、not found、
    stale、ahead、gap、storage、lifecycle 等映射；Bootstrap 不得提交业务
    command。
11. **idempotency**：key scope、canonical hash 算法和 golden vectors；
    same key/different hash 的冲突；receipt 字段、大小、状态、保留期和
    restart 后可查询性。
12. **transaction/rollback**：Task、History、revision、journal、receipt
    的同事务顺序；no-op/stale/rejected/rolledBack/cancel/pending/unknown
    的终态和 key reuse；commit 后 event/response 丢失的 reconcile。
13. **revision/journal**：profile 初值、每个实际变更事务恰好一个 revision、
    journal 不作 Event Sourcing、同一事务 change 不拆页、损坏/中间缺行
    的 gap 检测和 oldest 语义。
14. **read recovery**：GET CHANGES SINCE 的分页上界、after=current/
    after>current、gap/ahead、full snapshot、SnapshotRevision、模型应用
    失败时 LastSeen 不前进。
15. **WAL/schema/readiness**：WAL 启动校验、只读客户端禁止写 PRAGMA/
    migration/checkpoint、additive migration、migration/health 失败停止
    写且保留旧数据、禁止删库重建。
16. **restart/watchdog/safe mode**：状态机、计数窗口、backoff、marker、
    healthy/failed health 的读写权限、UI 提示、恢复条件和 control 权限。
17. **cutover**：pre-cutover 与 post-cutover 的最后/第一 runnable
    checkpoint；Main/Widget 直接 service、TaskWorkspace、SaveChanges、
    Migrate、P2 gate/fallback 的静态和运行时消失证据。
18. **验收证据**：构建、自动测试、隔离 profile/DB、PID/句柄、revision/
    journal/history/receipt 行数、进程退出码、日志脱敏、用户人工验收
    与工具 smoke 的分离；不得把固定 Instant、CLI/UIA 当用户跨午夜签字。

| T21 | RequestId matrix（补强） | 新连接/重试/status/cancel/reconnect 的 requestId 按冻结语义一致，logical key 稳定。 | 同一字段同时承担 attempt 和 logical identity，无法关联响应。 |
| T22 | receipt outcome matrix（补强） | changed/no-op/stale/rejected/rollback/cancel/timeout/unknown 每种终态可查询并按规则复用 key。 | 某个结果无 durable 事实或 key reuse 造成重新写入。 |
| T23 | canonical hash vectors（补强） | null/缺省、数字、Unicode、重复 key、未知字段、数组和 profile scope 均有确定结果。 | 不同 runtime 或字段排列产生不同 hash。 |
| T24 | resource/byte-order limits（补强） | frame 字节序、上限、in-flight、partial IO、deadline 和 close action 逐项可测。 | “建议”值没有实现一致性或大包导致 OOM/阻塞。 |
| T25 | Bootstrap and activation boundary（补强） | Bootstrap 无业务 DB handle/migration；当前 Activation 不能提交 command；control 权限不能读业务事实。 | Bootstrap 执行 SaveChanges/Migrate、activation payload 改 Task。 |
| T26 | read apply/atomic reorder（补强） | read model 应用失败保留旧模型且 LastSeen 不前进；reorder 的多条变化一个 Agent txn、无部分成功。 | 先推进 LastSeen 再应用、reorder 半成功、History/journal 不完整。 |

## 9. 后续人工验收步骤

以下步骤是未来实际二进制的验收脚本，不是本窗口执行记录。必须使用隔离
clone/profile 和全新或明确可恢复的测试数据，绝不使用
D:\Anime\.devdata\reminnote.sqlite；不得修改系统时间。命令、二进制版本、
ProfileScope、绝对 DB path 和预期 PID 必须在总成接入后填写为真实值，不能
用占位符收口。

### A. 启动、ready 和只读边界

1. 记录 commit、Windows 用户、profile、数据根、二进制版本和初始 DB
   revision；确认测试路径不在总成开发数据根。
2. 启动 Bootstrap，观察 Bootstrap、Agent、Main 的进程和 pipe；验证 Agent
   只有在 WAL、schema/migration、health、revision state 校验成功后才报告
   ready。
3. 在 Agent 尚未 ready 或 storage health 失败时启动 Main/Widget，验证它们
   不创建业务 writer、不执行 migration、不使用 P2 gate fallback，并按
   冻结规则显示 unavailable/stale/readonly。
4. 对每个进程记录 DB handle、connection mode、writer transaction 和日志；
   结果必须证明 Bootstrap 没有业务库句柄，Main/Widget 没有 writable
   SaveChanges 路径。

### B. Main → Agent → Widget 的真实 Task 链路

1. 由 Main 创建、改名、记录结果、更新 plan、排序、继续和删除已有 P2
   Task；每项命令经过 business pipe，带冻结的 RequestId、key 和
   ExpectedRevision。
2. Widget 读取同一 profile 的 read model，观察 Task/Today/History 和
   revision；Widget 的写动作只产生 Agent command，不打开第二 writer。
3. 检查每个实际变更事务恰好一个 global revision，Task、History、journal、
   receipt 同事务可见；no-op 不增加 revision。
4. 验证当前 P2 Activation pipe 只激活 host，不改变业务状态，也不接受
   Task/SQL/idempotency payload。

### C. 并发、ExpectedRevision 和原子 reorder

1. 两个客户端读取同一个 revision，分别提交不同写命令；按冻结规则验证
   一个提交、另一个 stale，或验证规定的冲突结果，不能出现未定义的双写。
2. stale 客户端 refresh 后用新 revision 和允许的新 key 重试；无 force
   写入，无旧 key 越权覆盖新状态。
3. 提交跨多个 Task 的 reorder，验证事务内所有 Task 变化、History、journal
   和 receipt 要么全部成功，要么全部回滚；一个 revision 的 change page
   不拆开同一事务。

### D. response loss、timeout、cancel 和幂等

1. 在 commit 前、commit 后分别丢弃 response；客户端只能显示
   confirming/unknown，并用 command.status、相同 key/hash 或 changes
   reconcile，不能立即生成第二个 key。
2. 断开并重连，验证 requestId 依照冻结语义、idempotencyKey 和 hash
   依照稳定逻辑命令语义；重放只返回首个事实，不增加 revision/history。
3. 测试相同 key/相同 hash、相同 key/不同 hash、pre-commit cancel、
   post-commit cancel 和 Agent restart 后 status；每种结果与 receipt
   outcome matrix 一致。

### E. changes、gap 和 full snapshot

1. 逐页获取 GET CHANGES SINCE，验证 after=current 为空、after>current
   是 ahead、合法旧 revision 增量连续且同事务不拆页。
2. 在隔离 fixture 中制造 oldest gap 和 journal interior gap；客户端必须
   转 full refresh/read-only，不能猜测缺失 change 或推进 LastSeen。
3. 让 read model 应用 snapshot 中途失败，验证旧模型和旧 LastSeen 保留；
   只有完整 snapshot 与 SnapshotRevision 原子应用后才更新 LastSeen。

### F. Agent restart、watchdog 和 safe mode

1. 正常停止/重启 Agent，验证 agentInstanceId、hello、reconnect、receipt
   和 changes 恢复；旧连接上的命令不能被默认为成功。
2. 在隔离 profile 注入 Agent crash，验证冻结的 restart window、次数、
   backoff、marker 和 safe mode 状态；不能无限重启、删除 DB 或回退到
   Main/Widget direct writer。
3. 分别验证健康 safe mode 和 health failure safe mode 的 Task 写权限、
   readonly 行为、UI 按钮和用户提示。

### G. 实例、用户隔离和权限

1. 启动第二 Main，验证既定激活行为；启动相同 WidgetInstanceId 和不同
   WidgetInstanceId，按 U1 的选择验证激活/并存。
2. 以另一个 Windows user 尝试连接、读取、提交、查询 status 和观察
   event；所有 business 操作必须被拒绝，且错误不泄露任务内容或 profile
   细节。
3. 验证 control/activation 权限不会自动获得 business read/write 权限，
   pipe scope 不跨用户/跨 profile。

### H. P2 回归、真实人工验收和范围门禁

1. 复跑 P2 Task/Today/Parser/History/Widget 既有验收，包含跨午夜规则和
   既有错误处理；不把本次 IPC smoke 视为产品签字。
2. 继续执行 P2 尚 Pending 的真实
   23:00 → 次日 00:30 → 01:00 用户人工路径，不改系统时间，不以固定
   Instant、CLI 或 UIA 代替用户观察和确认。
3. 检查数据库 schema、pipe traffic、logs 和进程列表，确认没有
   ReminderRule/Schedule/Instance/Scheduler/Toast/Tray/Anime/Sync/
   network/E2EE/updater 等提前进入 P2.5。

通用失败条件：任何双 writer、Bootstrap 业务库访问、Main/Widget direct
SaveChanges 或 fallback、重复幂等写、半事务、错误推进 LastSeen、未检测的
gap、跨用户访问、删库/无限 watchdog、激活 pipe 改业务状态、P2 语义回归、
