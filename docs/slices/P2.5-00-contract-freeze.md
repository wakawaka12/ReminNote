## 1. 结论、效力和证据边界

### 1.1 候选结论

本候选冻结以下不变主线：

1. Agent 是每个用户/profile 的唯一业务 writer。Task、Task History、global
   revision、Change Journal、command receipt、migration 以及未来同一 profile 的业务
   写入均只能经由 Agent writer actor。
2. Main 和 Widget 只通过 Agent business pipe 发高层命令；读模型使用同一 profile 的
   SQLite WAL 只读查询通道。它们没有业务 writable connection、SaveChanges、migration
   或 P2 direct-write fallback。
3. Bootstrap 只负责生命周期、单实例、激活、watchdog 和 safe mode；它不打开业务库、
   不迁移业务 schema、不解析/执行业务命令、不写业务事实。
4. 当前 Main Activation pipe 和 Widget Activation pipe 是 host activation/control
   通道，不是业务 IPC；不得把 Task payload、SQL、idempotencyKey、receipt 或业务
   response 塞入这些通道。
5. 每个实际业务变化事务恰好分配一个新的 global revision，并在同一事务提交 Task、
   必要 History、Change Journal 和最终 receipt；no-op、拒绝、stale、纯读和 receipt-only
   metadata 不伪造 revision。
6. RequestId 只关联一次 wire attempt；同一逻辑命令由当前 Windows user、ProfileScope、
   idempotencyKey 和 canonical payload hash 识别。重试创建新 RequestId，但复用 key/hash。
7. 事件是 best-effort hint；事实来自已提交 SQLite 和 receipt。重连、事件丢失、gap 或
   客户端状态应用失败都必须能通过 changes 或完整只读 snapshot 修复。
8. 任何可运行 checkpoint 只允许一条合法业务写入路径。P2 Main/Widget direct writer
   仅是 pre-cutover 历史路径；post-cutover 不与 Agent writer 共存。

## 3. Actor、进程和唯一业务 writer

### 3.1 首版拓扑

~~~text
当前 Windows user + canonical DataProfile
                    |
        +-----------v-----------+
        | Bootstrap (1/profile) |
        | start / activate /    |
        | watchdog / safe mode  |
        | no business DB        |
        +-----+------------+-----+
              |            |
        control only       |
              |            |
        +-----v------------v-----+
        | Agent (1/profile)      |
        | sole writer actor      |
        | transaction/revision   |
        | journal/receipt/events  |
        +-----+------------+-----+
              |            |
       business pipe       | read-only same DB
              |            |
       +------v-----+  +---v----------------+
       | Main       |  | Widget (N/instance)|
       | UI/client  |  | UI/client          |
       +------------+  +--------------------+
~~~

Agent “拥有 Widget”表示 Agent 拥有业务命令、revision/recovery 和生命周期协调，
不要求首版把 Widget 视觉树搬入 Agent 进程。即使未来同进程，也只能保留一个 Agent
writer actor。

### 3.2 职责矩阵

| Actor | 允许 | 禁止 |
|---|---|---|
| Bootstrap | 获取当前 user/profile 的实例资格；启动/激活 Agent、Main、Widget；等待控制健康握手；有限重启；维护 runtime safe marker | 打开业务 SQLite；执行 EF migration；创建 DbContext；调用 Task application service；解析/执行 business command；写 Task、History、revision、journal、receipt |
| Agent | 打开唯一业务 writable connection；执行 migration；串行接收和验证命令；同事务写 Task、History、revision、journal、receipt；发布 commit 后事件；提供 status/changes | 第二个业务 writer；commit 前发布成功事件；把未提交状态发给客户端；以 event 取代 durable journal；因客户端断开做半写 |
| Main | 只读 Today/read model；经 business pipe 发 P2 高层 command；维护 LastSeenRevision；使用 host activation | writable TaskWorkspace/DbContext；SaveChanges/SQL/PRAGMA 写入；migration；P2 write gate；Agent 不可用时 direct fallback |
| Widget | N 个独立 UI 实例；只读 Today/read model；经 business pipe 发允许的 P2 command；维护自身 LastSeenRevision；使用实例 activation | 第二 writer；保留 P2 gate 作为正式路径；用 Snooze/Reschedule 擅自改变未实现语义；Agent 不可用时落盘 |

业务写入包括 Task、Task History、设置、revision、Change Journal、command receipt、
schema migration 和任何改变上述事实的 SQL/EF 操作。只读查询不属于 writer，但必须
使用本文件规定的 read-only 连接和 snapshot 规则。

### 3.3 Bootstrap 和 Agent 的不可越界边界

- Bootstrap 只传递最小启动配置：ProfileScope、canonical DataRoot/profile、版本和
  safe-mode flag；不得把 Task 标题、Notes、receipt 或 Token 汇总进控制消息。
- Agent 是业务 schema owner 和唯一 migration owner。Bootstrap 的 health 判断只依据
  进程/控制握手，不通过打开业务库查询来判断。
- Bootstrap 启动失败、Agent 不可用、WAL/迁移/完整性失败时，结果只能是 unavailable、
  read-only 或 safe mode；绝不能让 Main/Widget 切回 P2 writer。
- 当前 Main Activation 和 Widget Activation 只传 activate/focus 等控制意图；不得传
  Task ID、标题、SQL、idempotencyKey、expectedRevision、业务 response 或事件。

| U6 safe mode | safe mode Agent 若 DB/WAL/schema health 通过，允许核心现有 P2 Task command 读写但禁用非核心扩展；若 health failed，只提供最后只读 snapshot/unavailable；两者都不允许 Main/Widget direct write。 | 健康故障可恢复日常 Task，未知故障优先保护数据；用户看到明确状态。 | safe mode 一律只读。 | 用户确认写按钮/故障提示后，连同安全手测和状态码一起改变。 |

## 5. P2 兼容边界和命令范围

P2.5 是架构迁移，不是产品功能扩张。P2 的 ANYTIME、TIME、RANGE、Today、Parser、
结果、History、改期、排序和 PARTIAL continuation 语义保持不变。P2.5-03 将它们包装成
高层 command，不暴露 SQL、EF entity、DbContext 或数据库路径。

| P2 行为 | 首版 operation | 必须在 Agent writer transaction 内重验证 |
|---|---|---|
| Quick Add/create | command.task.create | Parser、时间形状、标题上限、profile、当前 revision |
| Rename | command.task.rename | Task 存在、标题规则、未删除 |
| DONE/result | command.task.record_result | Task、结果与时间形状、RecordedAt、History |
| Plan change | command.task.update_plan | 无结果保护、日期/时间、旧计划 History |
| Same-group reorder | command.task.reorder | 同日期/分组、相邻 ID、两项 sort/history 的原子性 |
| PARTIAL continuation | command.task.continue | 源为 PARTIAL RANGE、新 UUID、continuation relation、History |
| Existing delete入口（若暴露） | command.task.delete | 删除边界、外键/历史语义和 current revision |

所有 mutation 都要求 key/hash/expectedRevision。没有 force、ignore-conflict 或
客户端传入低级 sort SQL 的路径。P2.5 不加入 Reminder、Anime、Sync、网络、E2EE、
updater、通用插件、Event Sourcing、新时间形状或完整 Recovery Center。

## 6. ProfileScope、canonical path 和 ACL

### 6.1 输入解析和路径优先级

1. 只接受明确命令行输入；不读取 cwd、环境变量、注册表或隐式用户目录作为业务 root。
2. explicit --data-root 的优先级最高；未提供时才接受 explicit --repo-root，并将 data
   root 派生为 repo-root\.devdata。这里的“优先级”是解析规则，不授权两个值同时使用。
   同时传入 --data-root 和 --repo-root 直接返回 bootstrap.args.ambiguous，不静默选择一个。
3. --repo-root 必须是绝对路径，canonical 后同时包含 .git 和 ReminNote.sln；无效、
   不存在、UNC/远程 root、reparse 后越出 root 或不能取得 final path 时拒绝，不创建未知
   目录或数据库。
4. --data-root 必须是绝对的本机 canonical directory；其 real path 不能是文件、UNC、
   远程路径或 reparse escape。Agent 只在路径检查和启动契约满足后创建/迁移 profile DB。
5. --profile 可省略，默认 default；显式值必须匹配
   [a-z0-9][a-z0-9._-]{0,63}，不可为 .、..，不可包含 slash、backslash、空白、冒号或
   Unicode 非 ASCII 字符。不同大小写不作为不同 profile；非小写输入拒绝而不隐式改名。
6. default profile 的 DB 为 canonical data root 下的 reminnote.sqlite，以保留 P2 的
   root\.devdata\reminnote.sqlite 兼容输入。非 default profile 的 DB 为
   root\profiles\profile\reminnote.sqlite。profile directory 只能由 Agent/Bootstrap
   按本契约创建，不由 Main/Widget 创建。
7. canonical path 使用 Windows final path：解析绝对路径、消除 . 和 ..、统一
   backslash、移除非 root 的末尾分隔符、统一 drive letter 和 Windows case-insensitive
   比较；现有 DB/parent 使用 GetFinalPathNameByHandle 等价能力验证 reparse 不越界。
   路径规范化失败即停止，不用字符串猜测。

### 6.2 ProfileScope 派生

ProfileScope 不是秘密，也不是唯一安全边界。Agent 从 OS token 和 canonical DB path
派生，不能接受客户端自报 SID 或路径作为权威：

~~~text
scopeInput =
  "ReminNote.ProfileScope.v1" + NUL +
  actualUserSid + NUL +
  canonicalDbPath

ProfileScope = "p1-" + lowercase-hex(SHA-256(UTF-8(scopeInput)))
~~~

actualUserSid 使用连接 token 取得的 SID 字符串；canonicalDbPath 为 6.1 结果。
business pipe 的名称为 Local\ReminNote.Agent.<ProfileScope>。同一个 canonical
DB path 和同一个 user 得到同一个 scope；不同 user 或不同 profile 不得共享 scope。
ProfileScope 变更视为不同 profile，不能把 receipt、LastSeen 或 DB 状态跨 scope 合并。

### 6.3 business/control/activation ACL

| endpoint | 名称形状 | 允许 payload | 业务权限 |
|---|---|---|---|
| Agent business | Local\ReminNote.Agent.<ProfileScope> | hello、P2 command、status、cancel、changes/event | 只允许当前 user SID；连接后再校验实际 SID 和 scope |
| Bootstrap/Agent control | Local\ReminNote.Control.<ProfileScope> | start、stop、health、safe-mode、activate 等 allow-list | 当前 user；如 OS 启动确需 SYSTEM，只授予 control，不授予业务读写 |
| Main activation | Local\ReminNote.Windows.Main.Activation.<ProfileScope> | activate/focus | control-only，不承载业务 envelope |
| Widget activation | Local\ReminNote.Widget.Activation.<ProfileScope>.<InstanceHash> | activate/focus | control-only；按 profile 和 WidgetInstanceId 隔离 |

business endpoint 的 DACL 不授予 Everyone、Users、Authenticated Users 或管理员
组的业务访问；不使用 Global 名称。control endpoint 的 SYSTEM 例外不能枚举、
读取、返回或提交 Task/History/revision/receipt。业务文件 ACL 同样遵循当前 profile
所有者最小权限，OS 必需的 SYSTEM 访问不能转化为应用层业务身份。

越权处理：

- 不匹配的 SID、ProfileScope、实例或 profile path 在业务 dispatcher 之前拒绝；
  可直接关闭连接，或只返回不带状态的 ipc.auth.access_denied。
- 不返回 currentRevision、oldestRevision、Task ID/title、receipt 是否存在、数据库
  绝对路径或另一 profile 的错误详情。
- ACL 通过仍不免除应用层 token 校验；知道 pipe 名称、猜到 scope 或拥有 control
  权限都不能取得业务读写权。

## 7. RequestId、幂等和 RN-CJ-1 canonical JSON

### 7.1 RequestId 与逻辑命令

- RequestId 是规范小写 UUID 字符串，每次 wire attempt 唯一。新连接、重连、retry、
  command.status 和 request.cancel 都生成新的 RequestId。
- 同一逻辑 mutation 的 durable identity 为
  (actualUserSid, ProfileScope, idempotencyKey, canonicalPayloadHash)。idempotencyKey
  是规范小写 UUID 字符串，长度固定 36；它不是 RequestId、clientInstanceId 或 Task ID。
- response 必须回显当前 attempt 的 RequestId；receipt 只保留首个/最近 attempt ID
  用于 bounded diagnostics，不以它做 dedup。retry 必须复用同一 key 和 hash。
- stale 后修改 expectedRevision、payload 或 operation 都是新的业务意图，必须生成新
  idempotencyKey。收到 response timeout、断管道或 Agent restart 时不得盲目生成新 key。

时序固定为：

~~~text
client attempt A(requestId=A, key=K, hash=H)
    -> Agent accepts/executes or records K,H
    <- response requestId=A may be lost
client reconnect attempt B(requestId=B, same K,H)
    -> command.status(K) or original command
    <- replay/original receipt, requestId=B, no second business transaction
~~~

### 7.2 RN-CJ-1 规范化算法

RN-CJ-1 的输入不是未经验证的任意 wire 文本，而是通过 v1 operation schema 验证、
完成明确默认值处理后的 effective command object。它适用于 write command 的 hash
preimage；requestId、clientInstanceId、sentAtUtc、timeoutMs 和 transport metadata
永远不进入 hash。

规范化步骤：

1. Frame 使用严格 UTF-8、无 BOM 解码；JSON 只允许 RFC 8259 的 object、array、string、
   number、true、false、null。NaN、Infinity、非标准注释和尾随逗号拒绝。
2. 解析器在原始 object 中拒绝重复 property name；所有字符串（包括 property name）
   做 Unicode NFC。NFC 后若两个 property name 相同，也拒绝，避免组合字符碰撞。
3. v1 write request 的 envelope 和 operation payload 对未知 property 采用 reject；缺省
   property 不自动变成空串、0 或 false。explicit null 与缺省永远不同。v1 当前 P2
   command 没有依赖隐式默认的 write field；未来若增加默认字段，必须在 schema 中先
   materialize 后再 hash，并更新 hashVersion/向量。
4. object property 按 NFC 后名称的 UTF-8 bytes 做无符号字典序递归排序。数组保持原顺序、
   不排序、不去重、不当作 set；数组顺序不同即 hash 不同。
5. string 输出为 NFC 后的 UTF-8。只转义双引号、反斜线和控制字符；使用 JSON 短转义
   b、f、n、r、t，其他 U+0000..U+001F 用小写十六进制 \u00xx；不转义 slash 和非
   ASCII Unicode。这样 composed/decomposed 的同一 NFC 字符得到同一 bytes。
6. number 必须匹配 JSON decimal grammar，按 exact base-10 decimal 解析，不经过 binary
   float。有效数字最多 38 个 significant digits，指数范围 -128..127，规范化 token
   最多 128 ASCII bytes；超出返回 ipc.request.invalid_number。去掉整数前导零和小数
   尾零，必要时把指数展开为 plain decimal；1.0 等于 1，1e3 等于 1000，
   1e-3 等于 0.001，-0、-0.0 等于 0。expectedRevision 另须在 signed 64-bit 非负
   范围内。
7. true、false、null 输出小写 JSON literal。object 缺省 key 不输出；explicit null
   输出 null。未知字段不是“先忽略再 hash”，而是 v1 write 的稳定拒绝。
8. canonical JSON 不加入空白、换行或 BOM；输出为一个 JSON document 的 UTF-8 bytes。
   所有实现必须通过本节的 golden vectors，不得使用本地 serializer 默认顺序。

hash preimage 是一个字段精确的 object：

~~~json
{"expectedRevision":0,"hashVersion":"rn-cj-1","operation":"command.task.create","payload":{"timeSpec":{"localDate":"2026-08-30","type":"ANYTIME"},"title":"x"},"profileScope":"p-demo"}
~~~

上例展示的是实际排序后的成员集合；字段顺序由 RN-CJ-1 的 bytes 字典序决定。
当前 preimage 的成员只允许 expectedRevision、hashVersion、operation、payload、
profileScope；不能加入 key、RequestId、标题回显或任意 diagnostic 字段。hash 为
SHA-256(canonical UTF-8 bytes)，存储 32-byte binary，并以 64 位小写 hex 传输/诊断。

## 8. Receipt、状态、key reuse 和事务

### 8.1 Receipt 形状和持久化

command_receipt 的逻辑唯一键为 (actualUserSid, ProfileScope, idempotencyKey)；至少保存：

- operation、hashVersion、32-byte canonicalPayloadHash；
- status、changed、committedRevision nullable；
- errorCode nullable、firstAcceptedAtUtc、updatedAtUtc；
- firstRequestId/lastRequestId 仅用于有限诊断；
- bounded attempt count 和 AgentInstanceId 诊断值。

不得保存完整 Task title、Notes、attachment、Token、Authorization/header、SQL、原始
frame 或完整 payload。成功 result 和 error details 只保存经过 allow-list、大小限制的
可重放内容。

接受流程为：

1. Agent 在唯一 writer actor 中完成 auth、version、schema、hash 和 key 冲突检查。
2. 对新的 key/hash 先以 receipt-only transaction 建立 PENDING 行；该 metadata transaction
   不分配 global revision，也不写 Change Journal。
3. 随后最多执行一个 domain write transaction：重新读取 current revision，检查
   expectedRevision，重新验证 domain；变化时写 Task/History，分配 revision，写 journal，
   将 receipt 更新为 COMMITTED，并 COMMIT。最终 receipt 和业务事实同一事务提交。
4. no-op 将 receipt 更新为 COMMITTED、changed=false、committedRevision=currentRevision，
   不写 journal、不增加 revision；receipt-only 写入不算业务变化。
5. stale/domain reject 在没有业务事实的 receipt-only transaction 中写相应 rejected
   status；事务异常先回滚全部 domain 写，再尽力把 receipt 标为 ROLLED_BACK。若连
   receipt 更新都失败，status 只能向客户端报告 unknown，不能声称 rollback。
6. COMMITTED 后才发 changes.available event，再返回 response；event/response 任一丢失
   都由 receipt/status/changes 对账。

### 8.2 结果矩阵

| 外部 outcome | 持久 status | changed / CommittedRevision | 首次 response | 同 key + 同 hash | 同 key + 不同 hash |
|---|---|---|---|---|---|
| changed | COMMITTED | true / 新 revision R | ok=true，changed，committedRevision=R | replayed=true，返回原结果，不写 | ipc.idempotency.conflict |
| no-op | COMMITTED | false / 当前 revision R | ok=true，changed=false，不造 revision | replayed=true，仍为 no-op | conflict |
| replayed | 原 receipt status；不是独立持久状态 | 使用原 receipt 的值 | 不适用；是 response overlay | 只读回放，replayed=true | conflict |
| stale | REJECTED_STALE | false / null | ok=false，revision.expected_mismatch，retryable=false | replay 同一 stale | conflict；刷新后新 key |
| rejected | REJECTED | false / null | ok=false，稳定 domain code，retryable 按错误码 | replay 同一拒绝 | 修改意图必须新 key |
| rollback | ROLLED_BACK（若可写 receipt） | false / null | ok=false，storage.transaction_failed，retryable=true | 同 key/hash 可重新尝试一次 domain command，不重复旧事实 | conflict |
| cancel before commit | CANCELLED | false / null | ok=false，ipc.request.cancelled，retryable=false | replay cancel；要故意重新执行须新 key | conflict |
| timeout before transaction | TIMED_OUT | false / null | ok=false，ipc.request.timeout，retryable=true | 同 key/hash 可重新进入 PENDING；不得并行第二次 | conflict |
| client-only timeout / response loss | PENDING、COMMITTED 或 UNKNOWN，取决于 Agent 事实 | 未知时 null | 客户端显示 confirming，不伪造 ok/failed | status/原命令用同 key/hash 对账 | conflict |
| unknown after crash/storage failure | UNKNOWN，或仍为 PENDING 但向客户端映射 unknown | null；不声称 rollback | ok=false，outcome=unknown，retryable=true | 先 status + changes/snapshot；同 key/hash 可安全继续 | conflict |

额外规则：

- receipt status 的 changed/no-op/replayed/stale/rejected/rollback/cancel/timeout/unknown
  均有上述明确 persistence、CommittedRevision 和 key reuse 语义。
- Agent 看到同 key/hash 的 COMMITTED、REJECTED、CANCELLED 等已有终态时，不重新执行
  domain logic；只回放 allow-list result/error。TIMED_OUT/ROLLED_BACK/UNKNOWN 只能按
  表中规则串行重新进入一次处理。
- command.status 读取 receipt，不改变 business fact、revision 或 journal。不存在 key
  返回 ipc.request.not_found，不泄露其他 scope 的存在性。
- client CancellationToken 的本地取消不等于 server cancel；若不发送 request.cancel，
  客户端必须仍按 unknown/response loss 对账。
- P2.5 默认永不自动删除 receipt/journal。未来 retention 必须记录
  oldestAvailableRevision 和 receipt expiry，并让过期 key 返回明确的 expired/unknown
  结果；不能把已删除 key 当作从未使用而重新执行。

### 8.3 单命令事务和故障

Agent writer actor 串行排队；一个 mutation 的 domain part 只有一个事务：

~~~text
BEGIN IMMEDIATE
  read current revision and compare expectedRevision
  reload and validate domain
  if changed:
      write Task / History
      allocate current + 1 exactly once
      write all Change Journal rows with same revision
  if no-op:
      do not allocate revision/journal
  write final receipt state
COMMIT
after COMMIT: publish event, then response
~~~

预期 revision 必须在取得 writer transaction 后再次读取和比较；不能在排队前检查一次
后等待。事务异常、commit failure、process crash before commit 均不得留下部分 Task、
History、revision、journal 或最终 COMMITTED receipt。DbContext/change tracker 在失败
后必须丢弃，不能把脏实体带给下一命令。

Agent 在 commit 后、response/event 前崩溃时，新的 Agent 通过已提交 receipt/revision
发现事实；客户端不得以 timeout 生成新 key。commit 前 cancel 只能在安全取消点回滚；
进入 commit 后 cancel 不撤销事实，结果按 COMMITTED 回放。

## 9. Envelope、status/cancel 和稳定错误码

### 9.1 Request envelope

业务 pipe 的 v1 request 使用 camelCase、UTF-8、无 BOM；下列字段都是固定规则：

| 字段 | 必填 | 规则 |
|---|---|---|
| protocolVersion | 是 | 严格 major.minor 字符串，当前 1.0 |
| messageType | 是 | 必须为 request |
| requestId | 是 | 当前 wire attempt 的小写 UUID |
| clientKind | 是 | main 或 widget；bootstrap 只允许 control endpoint |
| clientInstanceId | 是 | 进程启动生成的小写 UUID，重启改变 |
| sentAtUtc | 是 | UTC RFC3339，供诊断，不作为服务端 deadline |
| timeoutMs | 是 | 1..30000 整数，受第 10 节默认和上限约束 |
| operation | 是 | allow-list operation string，最长 96 bytes |
| payload | 是 | object；无 payload 也发送 {}，不能缺省 |
| idempotencyKey | mutation 必填 | 小写 UUID；hello/status/changes/cancel 不填 |
| expectedRevision | mutation 必填 | 非负 signed 64-bit 整数；hello/status/changes/cancel 不填 |

客户端不发送实际 SID 作为可信身份；hello 里的 profile hint 也只用于比对，权威值由
pipe endpoint 和 OS token 取得。未知 operation、messageType、required field 或 enum
必须拒绝。

### 9.2 Response/error envelope

对已通过连接身份检查的业务 request，response 必须包含以下字段，即使值为 null：

~~~json
{
  "protocolVersion": "1.0",
  "messageType": "response",
  "requestId": "current-attempt-uuid",
  "operation": "command.task.record_result",
  "agentInstanceId": "agent-instance-uuid",
  "serverRevision": 43,
  "ok": true,
  "replayed": false,
  "outcome": "changed",
  "committedRevision": 43,
  "payload": {},
  "error": null
}
~~~

- outcome 必填，允许 changed、no-op、replayed、stale、rejected、rolledBack、cancelled、
  timeout、pending、unknown。
- committedRevision 必须是非负整数或 null；没有实际业务 commit 时为 null。no-op 使用
  当前 revision 作为对账位置，但不表示它分配了新 revision。
- ok=true 时 error 必须为 null；ok=false 时 payload 必须为 null，防止“错误但带半个
  成功结果”。replayed=true 只表示从 durable receipt 回放，不代表本次重新写入。
- serverRevision 是 Agent 生成 response 时知道的 current revision；客户端不能据此
  认为 read model 已经应用。agentInstanceId 重启后改变。
- error 必须为 object，包含 code、retryable、details；details 必须为 object，即使空
  也发送 {}。humanMessage 可选且最多 512 bytes，只能做人类提示，不能做机器分支。
- details 是 allow-list machine fields，最多 8192 bytes；不得有 title、Notes、附件、
  Token、Authorization/header、数据库绝对路径、SQL、完整 payload、其他 profile 状态
  或任意未截断异常堆栈。
- 成功 payload 最多 16384 bytes，只允许 operation 声明的安全结果字段；错误不得回显
  原始请求。未知 response field 在 v1 client 中忽略，不能影响已知字段语义。

### 9.3 event、status 和 cancel

event 是单向 best-effort message，必须包含：

| 字段 | 规则 |
|---|---|
| protocolVersion/messageType | 1.0 / event |
| eventId | 每次 event 的小写 UUID |
| eventType | 当前至少 changes.available |
| agentInstanceId | 当前 Agent instance UUID |
| occurredAtUtc | commit 后 UTC 时间 |
| revision | 事件对应的 global revision |
| payload | 最大 64 KiB，只含 scope、revision、entity ID/type、change kind 等安全元数据 |

changes.available 的 payload 至少有 fromRevision 和 toRevision。事件可丢失、重复、乱序；
客户端必须用 GET CHANGES SINCE 恢复，不能把 event 当唯一事实。

command.status request：

~~~json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "new-status-attempt-uuid",
  "clientKind": "main",
  "clientInstanceId": "client-uuid",
  "sentAtUtc": "2026-08-30T00:00:00.000Z",
  "timeoutMs": 2000,
  "operation": "command.status",
  "payload": {"idempotencyKey": "original-key-uuid"}
}
~~~

status response 只返回 status、operation、canonicalPayloadHash、changed、
committedRevision、errorCode、retryable 等 bounded metadata；不返回 Task title/Notes
或完整 payload。pending 表示继续等待/重连，committed 表示回放并刷新，rolledBack/
cancelled 按矩阵处理，unknown 先 changes/snapshot 再按原 key/hash 继续，not_found
只对当前 scope 返回。

request.cancel 使用新的 RequestId，无 idempotencyKey、expectedRevision；payload 必须有
targetRequestId 和 targetIdempotencyKey。它是 best-effort control request，不改变业务
事实。commit 前被接受时目标 receipt 为 CANCELLED；commit 获胜时返回目标已 committed；
没有 target、目标不属于当前 user/profile 或目标格式非法时返回稳定错误且不泄露状态。

## 10. Length-prefixed framing、资源和关闭

### 10.1 固定数值

| 资源 | 默认/上限 | 说明 |
|---|---:|---|
| length prefix | 4 bytes | unsigned big-endian；长度不含 prefix |
| frame | 1..1,048,576 bytes | 0、负值（若实现类型可表达）、超过上限拒绝 |
| write command payload | 262,144 bytes | canonical UTF-8；超出拒绝 |
| event payload | 65,536 bytes | 不含敏感文本 |
| error.details | 8,192 bytes | bounded allow-list object |
| success/status payload | 16,384 bytes | receipt 可重放字段上限 |
| JSON nesting depth | 32 | 超过即 invalid request |
| 单 connection in-flight | 32 | 超出返回 ipc.request.overloaded |
| 单 profile Agent queued request | 256 | 超出停止接收新 mutation，不能无界排队 |
| connect deadline | 2,000 ms | client default |
| hello/query/status read deadline | 2,000 ms | I/O 和 overall budget 取更小者 |
| mutation default timeoutMs | 5,000 ms | 客户端可传更小/更大但不得超过 30,000 |
| cancel timeoutMs | 1,000 ms | 不等待目标事务无限期 |
| absolute request deadline | 30,000 ms | 客户端和 Agent 硬上限 |

### 10.2 parser 和 byte stream 行为

- 发送方先写完整 4-byte big-endian length，再循环写完整 frame；接收方先循环读满
  prefix，验证 1..1 MiB 后才分配对应 buffer，再循环读满 frame。
- partial read/write、一次返回少于请求字节、多个 frame 合并、一个 frame 分多次到达都
  必须正确处理；zero-byte read 或 EOF 视为连接关闭。
- length 为 0、超过上限、整数计算溢出、prefix 截断、frame 截断、非法 UTF-8 均不进入
  JSON parser 和业务 dispatcher。可以返回不含 details 的 invalid_frame 后关闭；无法
  建立可靠边界时直接关闭。
- 有效 UTF-8 但非法 JSON 可返回 ipc.protocol.invalid_json 后关闭该连接；不执行业务。
  不得为了错误文案回显 frame。
- duplex connection 允许 event/response 交错。客户端按 messageType、requestId
  demultiplex；不能假定 response 是下一条消息。event 没有 requestId，response 必须
  回显当前 attempt requestId。
- timeoutMs 是客户端等待预算，不是 SQLite commit 的强杀。I/O/overall deadline 到期后
  客户端显示 confirming/unknown；Agent 已进入 commit 时必须完整 COMMIT 或 ROLLBACK。
- pipe close 后 outstanding request 不自动当作 cancelled/failed；它们按矩阵进入
  pending/unknown，使用同 key/hash 的 status、changes 或原 command 对账。
- 关闭、版本失败、ACL 失败和 frame 攻击都不能触碰 Task、History、revision、journal
  或成功 receipt。

## 11. ProtocolVersion、hello/ready 和 feature downgrade

### 11.1 协商

ProtocolVersion 是 ASCII 的 major.minor，禁止前导零、空白和额外段。当前候选的
supported set 只有 1.0，但算法先固定以支持未来 minor：

1. business connection 第一条 frame 必须是 session.hello；未 hello/重复 hello/先发
   command 都返回协议错误或关闭，不能写业务。
2. client hello 提供 supportedProtocolVersions（1..8 项）、requestedFeatures、
   requiredFeatures、lastSeenRevision 和 profile hint。server 只用 endpoint scope 和
   OS token 作为身份。
3. 如果没有共同 major，返回 ipc.protocol.unsupported_version（若 framing/身份允许）
   后关闭；不尝试把 major 当 minor。
4. 在共同 major 中选择双方支持的最高共同 minor，且不得高于 client 可处理范围。
   未来 server 不能把只在更高 minor 才定义的必填字段发给降级 client。
5. acceptedFeatures 是 client requested/required 与 server capabilities 的交集。
   未知或非 required feature 放入 downgradedFeatures；required feature 缺失返回
   ipc.protocol.feature_required，ready=false，关闭或等待升级。
6. v1 当前 capabilities 至少为 changes.available、changes.get_since、command.status、
   request.cancel、readonly-snapshot-v1。server response 返回 selectedProtocolVersion、
   acceptedFeatures、downgradedFeatures、agentInstanceId、currentRevision、
   oldestAvailableRevision 和 storage/readiness flags。

### 11.2 ready 状态

hello response 的 ready=true 仅在以下条件全部成立时出现：SID/profile 校验通过、
版本/feature 协商完成、Agent instance 存活、schema/migration/WAL/foreign key/integrity
健康通过、唯一 writer lease 已持有。safe healthy 可以 ready=true、safeMode=true、
writable=true；safe health failed 必须 ready=false、writable=false。

未 ready 时只允许再次 hello（按协议规则）和有限生命周期控制，禁止 command.task、
changes 写入或任何业务 mutation。Main/Widget 只能显示 stale/unavailable/readonly，
不得使用 P2 application service。

### 11.3 unknown fields

- v1 request 的 unknown envelope field、unknown operation payload field、重复 field、
  缺省 required field 一律稳定拒绝；不能“忽略后继续 hash”。
- response/event 的非 required unknown field 可被旧客户端忽略；旧客户端仍必须校验所有
  known required field 和 enum。server 只在协商到对应 minor/feature 后发送新增语义。
- future minor 若引入 extension object，必须明确定义是否参与 canonical hash；语义相关
  字段必须 bump hashVersion，诊断 extension 不得影响业务执行。

## 12. Global revision、Changes、snapshot 和 LastSeen

### 12.1 Revision/journal 逻辑模型

每个 profile 一行 revision_state：

~~~text
ProfileScope (唯一)
CurrentRevision: non-negative signed 64-bit
OldestAvailableRevision: 0 when no journal row, otherwise first retained revision
~~~

change_journal 至少有 ProfileScope、Revision、ChangeOrdinal、BatchId、EntityType、
EntityId、ChangeKind、ChangedAtUtc；(ProfileScope, Revision, ChangeOrdinal) 唯一。

- 初始 CurrentRevision=0，合法第一变化 revision=1。
- 只有实际业务变化的 transaction 分配新 revision；同一 transaction 的任意 Task、
  History 和 journal rows 共用该 revision 和 BatchId。
- failed/rejected/stale/no-op/pure read/receipt-only 不分配 revision；Change Journal
  是增量通知/恢复元数据，不是 Event Sourcing，不保存完整事件回放或替代用户 History。
- 在无 retention 的 v1，current>0 时 oldestAvailableRevision=1；current=0 时为 0。
  retention 未来必须原子更新 oldest 和 gap 规则。

### 12.2 GET CHANGES SINCE

operation 使用 changes.get_since；请求 payload：

~~~json
{"afterRevision":0,"maxRevisions":64}
~~~

规则：

1. afterRevision 必须是 0..9223372036854775807 的整数；不能为负、浮点、字符串。
   maxRevisions 必须是 1..128；0、负数、极大值返回 ipc.request.invalid，不静默变成
   默认或无限。
2. Agent 在一个 read snapshot 开始时取得 upper bound U=CurrentRevision，并只返回
   afterRevision < revision <= U 的完整 revision batch。response 包含
   snapshotUpperBound=U、fromExclusive、toInclusive、hasMore 和 batches。
3. afterRevision=CurrentRevision（含 0/0）返回空 batches，toInclusive=after，且不是
   gap。afterRevision>U 返回 revision.ahead；不能用整数加一溢出。
4. after=0、first available revision=1 是合法起点。若 oldestAvailableRevision>0 且
   after+1 < oldestAvailableRevision，则返回 revision.gap、fullRefreshRequired=true，
   不返回部分 batch。
5. server 必须验证所选 [after+1, toInclusive] 每个 revision 都至少有 journal row，
   min/max/count 连续，且 batch/BatchId 没有内部缺行。只凭 oldestAvailable 不足以通过
   检查；发现 interior gap、损坏或 batch 不完整也返回 revision.gap/storage.integrity_failed。
6. maxRevisions 按 revision 数而非 journal row 数计数。一个 revision 的全部 journal rows
   必须在同一页；若单个 batch 超过安全 payload 上限，返回稳定 storage.receipt_capacity/
   revision.batch_too_large，不拆成可误用的半批。
7. snapshot upper bound 避免并发写入把页面前后界线混合。若 U 大于 page 的 toInclusive，
   客户端以 toInclusive 请求下一页；若读取/应用失败，旧 model 和 LastSeen 都保留。

### 12.3 Read-only snapshot 和 LastSeen 原子推进

U2 选择的 query adapter 使用 canonical DB path 的 read-only connection，打开同一
SQLite read transaction：

~~~text
BEGIN (read-only)
  read revision_state.CurrentRevision as SnapshotRevision
  read complete Today/read model rows
COMMIT read transaction
~~~

返回的 read model、SnapshotRevision 和 freshness status 属于同一 snapshot。Main/Widget
不得执行 EnsureCreated、Migrate、SaveChanges、INSERT/UPDATE/DELETE、write PRAGMA、
wal_checkpoint、VACUUM 或任何 schema 操作；连接必须是 OS/driver read-only + query-only
配置。Agent 是唯一初始化 WAL、foreign key 和 schema 的 actor。

客户端 read state 用一个 atomic swap 更新：

1. 取得完整 changes page 或完整 snapshot；
2. 在内存中验证并应用全部 batch/rows；
3. 应用成功后一次性替换 read model 和 LastSeenRevision；
4. 任意应用、反序列化或 snapshot 失败都保留旧 model、旧 LastSeen，并显示 stale/
   unavailable；不能先推进 LastSeen。

Agent 不可用但 DB 可安全只读时可以显示最后一份 snapshot，状态必须标 stale，写按钮
禁用；不能称为刚刚从 Agent ready 得到的 fresh state。read connection 无法保证 schema/
snapshot 对应时，放弃此次结果并重新取完整 snapshot。

## 13. Widget instance 和 activation 细则

- WidgetInstanceId 是启动器/快捷方式提供的稳定 ASCII key，不从 PID、窗口句柄或每次
  启动的随机数派生；缺省为 default，长度和字符规则与 profile key 相同。
- clientInstanceId 是每次进程启动新的 UUID；它与 WidgetInstanceId 不同。前者关联
  wire client，后者决定用户想要的 widget 拓扑。
- instance mutex/activation 名称绑定 Local、actual user、ProfileScope 和
  InstanceHash。相同 ID 的后启动进程只发送 activate/focus，收到成功后退出；它不能
  创建 Agent、打开业务 writer 或提交 command。
- 不同 WidgetInstanceId 可同时运行并读取同一 profile；所有 mutation 仍经同一 Agent
  queue，不能按实例分裂 revision 或 receipt。
- Widget 崩溃/退出只释放自身窗口和 client connection；Agent 不因单个 Widget 退出而
  停止，其他 Widget/Main 也不被当作需要重新创建的 writer。
- 当前 P2 的无 ProfileScope activation/mutex 只属于 pre-cutover host 事实；post-cutover
  business endpoint 不得复用它，activation scope/ACL 必须按第 6 节生成。

## 14. Watchdog、Safe Mode、marker 和失败状态

### 14.1 状态机和数值

~~~text
STOPPED
  -> NORMAL_STARTING
  -> NORMAL_HEALTHY
  -> (crash / not-ready / heartbeat failure)
  -> RETRY_WAIT
  -> NORMAL_STARTING              [最多 3 次普通恢复尝试]
  -> SAFE_STARTING
  -> SAFE_HEALTHY | SAFE_UNHEALTHY

任一状态 -> STOPPING -> STOPPED
~~~

- failure window 为 10 分钟，从第一次 normal start failure/crash 计时；普通恢复尝试
  最多 3 次，backoff 固定为 1 秒、2 秒、5 秒。第三次仍未 ready 后不再普通重启，
  进入 SAFE_STARTING；不允许无限 crash loop。
- NORMAL_HEALTHY 连续健康 10 分钟后，滚动失败计数可归零，但 safe marker 不因启动成功
  而悄悄删除。marker 只有用户明确选择 Resume normal mode，且 normal Agent 连续健康
  10 分钟后才原子清除；若失败，保留 marker 和失败原因。
- SAFE_HEALTHY：Agent 的 DB/WAL/schema/integrity/unique-writer health 通过；可提供
  核心 P2 Task read/write，但 UI 显示 safe mode，非核心扩展关闭。
- SAFE_UNHEALTHY：health 未通过；Agent 不执行 migration repair 或普通 mutation；Main/
  Widget 只能读最后可用 snapshot 或显示 unavailable，所有写入 disabled。
- safe mode 的两个分支都禁止 Main/Widget direct writer、P2 Semaphore fallback、删库、
  覆盖原 DB 或启动第二 Agent。用户看到的状态码至少为 lifecycle.safe_mode、
  storage.not_ready 或 storage.read_only。
- Bootstrap 只观察进程、控制握手、heartbeat 和 marker，不打开业务 DB。Agent 负责
  storage health；Bootstrap 不能因为 health 失败而绕过 Agent。

### 14.2 marker 和 ACL

runtime marker 位于 canonical profile directory 的 runtime\agent-health.json，不在
业务 DB 内。marker 只含 schemaVersion、state、windowStartUtc、failureCount、
nextRetryAtUtc、lastReasonCode、lastAgentInstanceId 等 bounded non-sensitive metadata，
最大 4 KiB；不含 Task、path secret、Token 或 payload。

Bootstrap 通过同目录临时文件写入、flush/write-through、同目录原子 replace；不能先删
旧 marker 再写新 marker。目录和 marker DACL 只授予当前 user SID 的 full control；若
SYSTEM 是 OS 启动必需者，只授予 control 所需的最小访问，不授予 business payload
访问。不得授予 Everyone、Users、管理员组的业务/marker写权限。

### 14.3 启停和用户反馈

- Bootstrap 先取得实例资格，再启动/激活唯一 Agent；Agent 报 ready 后才允许 Main/
  Widget business client 发 mutation。
- 正常 stop 进入 STOPPING，停止接收新 mutation，已接受 command 完成 commit/rollback；
  未确认 command 仍按 receipt 对账。
- crash/pipe disconnect/health failure 的 UI 文案按稳定 code 映射，不把“超时”写成
  “已失败”或“肯定未写入”。safe healthy 的写按钮可用但带 banner；safe unhealthy
  的写按钮禁用并告诉用户等待/恢复路径。

## 15. Single cutover、migration 和 writer proof

### 15.1 精确 checkpoint

| checkpoint | 唯一允许的业务 writer | 可运行含义 |
|---|---|---|
| P2-PRE-CUTOVER-LAST | P2 Main/Widget direct writer，经 P2 application service/命名 write gate | 最后一个旧 runnable；Agent business writer 不启动、不接受业务命令 |
| P2.5 build/intermediate | 无可宣称的产品 runnable writer，或只运行 test fake | 可编译/可做隔离测试，但不得作为发布组合；不能同时运行 Agent 与 P2 direct writer |
| P2.5-POST-CUTOVER-FIRST | Agent writer only；Main/Widget read-only + Agent command client | 第一个新 runnable；所有 P2 direct writer registration/path 已移除并通过证明 |

P2 direct writer 只能作为 pre-cutover 历史路径存在；在任何 post-cutover runnable
checkpoint，不得保留“平时不用”的 writable TaskWorkspace、P2 gate 或 fallback。

### 15.2 单一切换顺序

1. 总成保存并标识 P2-PRE-CUTOVER-LAST 的 commit、binary、schema、DB backup/路径和
   进程清单；停止所有 P2 Main/Widget，不在运行中混切。
2. 总成先接入唯一 public Core contract，再由 Agent owner 串行完成 additive migration、
   WAL/foreign key/schema/integrity/receipt readiness；migration 失败则 Agent not-ready，
   保留原文件和日志，停止普通写，不删库/重建/覆盖。
3. post-cutover writer-generation marker/版本 fence 由 Bootstrap/Agent 控制；旧 P2
   binary 不得由 Bootstrap 启动到 post profile。旧 binary 与 post Agent 共存不是支持
   的组合。
4. 启动唯一 Bootstrap/Agent，等待 ready；启动 Main/Widget client。Main/Widget 只有
   read-only handle 和 business pipe client。
5. 先做静态禁项扫描，再做 runtime writer proof；任一项发现 direct writer、未知
   writable handle、双 Agent 或旧 binary，立即停止所有业务写并将 checkpoint 判失败。
6. 只在上述证明通过后将 P2.5-POST-CUTOVER-FIRST 标为 runnable，继续 P2.5-05 至
   P2.5-08 门禁。中间 commit、fake、CLI smoke 不能改名为 post-cutover。

### 15.3 静态扫描禁项

P2.5-08 对 Main、Widget、Bootstrap 的生产源和生产 DI 做 AST/文本双重扫描；生成的
obj/bin、文档和明确 test-only fixture 先排除，再逐个审查匹配。以下禁项在 post-cutover
production path 必须为零个未豁免匹配：

**Main/Widget：**

- writable TaskWorkspace 构造、注册或 factory；P2 ITaskApplicationService writable
  registration/injection；
- DbContext/SqliteConnection 以 ReadWrite、ReadWriteCreate、Create 或可写 connection
  string 打开；直接打开业务 DB file handle；
- SaveChanges、SaveChangesAsync、ExecuteSql、INSERT、UPDATE、DELETE、EnsureCreated、
  Migrate、Database.Migrate；
- 写入 PRAGMA、journal_mode、wal_checkpoint、VACUUM、schema/table/index 创建；
- CrossProcessTaskWriteGate、Local\ReminNote.P2.TaskWrite、Semaphore/Mutex 作为
  业务写保护；
- Agent 不可用时调用 P2 application service、TaskWorkspace、直接 SQL 或任何
  “fallback/direct/local write”分支；
- 把 current P2 Activation pipe 当成 business pipe，或向 activation payload 加入
  Task/SQL/idempotency/receipt 字段。

**Bootstrap：**

- SqliteConnection、DbContext、TaskWorkspace、ITaskApplicationService、SaveChanges、
  EnsureCreated、Migrate、Database.Migrate、业务 SQL/PRAGMA；
- command.task.*、业务 payload/parser、Task/History/revision/journal/receipt 读写；
- 通过打开 DB 而不是 control handshake 实现 health；Agent 启动失败时启动 Main/Widget
  direct writer 或释放 P2 gate；
- 将 control endpoint 升级成 business endpoint。

**所有 production host：**

- 第二个 writer actor、第二套 migration owner、共享 service locator 取得 writable
  connection、旧 binary compatibility flag 允许双写；
- 未声明的业务 DB path、profile fallback、Global pipe/mutex、Everyone/Users business
  ACL；
- 用 event、UI toast、内存队列或 response 文案代替 durable receipt/journal。

扫描命令、排除规则和每个匹配的分类必须进入 P2.5-08 证据；“关键字没搜到”不足以证明
DI/反射/工厂间接路径不存在。

### 15.4 runtime writer proof 和失败处理

P2.5-08 必须在隔离 clone/profile 记录：

- commit、binary absolute path、Windows user/SID、ProfileScope、canonical DB path；
- Bootstrap、Agent、Main、每个 Widget 的 PID、AgentInstanceId、退出码；
- DB handle/connection mode：只有 Agent 有 writable handle；Main/Widget 只能 read-only；
- Agent writer transaction 的 begin/commit/rollback、revision、Task/History/journal/
  receipt 对照；同一变化只有一个 writer PID；
- Agent 停止后 Main/Widget 的写尝试返回 unavailable/read-only，DB/History/revision/
  journal/receipt 无变化；不能静默转 direct path；
- static scan zero list、旧 binary/version fence 结果和 activation/control traffic
  不含业务 payload。

若 migration、WAL、health、ACL、runtime proof 任一失败：

- Agent 不报告 ready，停止新 mutation；Main/Widget 保留旧 read model 并显示状态；
- 不删除/覆盖/重建原 DB，不自动修复唯一文件，不恢复 P2 direct writer；
- 若旧 binary 被观察到与 post Agent 共存，停止所有业务写，标记
  lifecycle.writer_generation_conflict，离线停止进程并由总成选择兼容 checkpoint；
- 任何 live rollback 必须先停止全部进程、核对备份/schema/兼容性，再回到完整的
  P2-PRE-CUTOVER-LAST 组合；不允许只替换一个 exe 或只降级一个 DLL。

### P2.5-05 Main client gate

- Main Today/read model 只经同库 read-only adapter；mutation 只经 Agent command client。

### P2.5-08 single cutover gate

1. P2-PRE-CUTOVER-LAST 和 P2.5-POST-CUTOVER-FIRST 的清晰 commit/binary/schema 边界；

## 19. 未来人工验收步骤

以下是 P2.5-08 后才可交给用户的验收稿。不是本窗口执行记录。必须使用新的隔离
clone、隔离 DataRoot/profile 和可恢复测试数据；不得使用 D:\Anime\.devdata\reminnote.sqlite，

### A. 环境、身份和启动顺序

1. 记录 build commit、binary absolute paths、Windows user/SID、ProfileScope、canonical
   DB path、SDK/configuration、初始 revision 和所有 PID；确认 profile 不在用户正式
   .devdata。
2. 使用 P2.5-07 提供的明确 Bootstrap 命令，显式传 --repo-root 或 --data-root（不同时

3. 启动 Bootstrap，观察只存在一个 Bootstrap 和一个 Agent；Agent 未完成 schema/WAL/

   不 migrate、不走 P2 fallback。
4. 用静态/runtime 证据确认 Bootstrap 没有业务 DB handle，Main/Widget 没有 writable
   handle，只有 Agent 可记录 writer transaction。

### B. Main → Agent → Widget 真实 Task 链路

1. Main Quick Add/create、rename、result、plan、同组 reorder、PARTIAL continue 和已有
   delete（若暴露）均通过 business pipe；每个 mutation 带新 attempt RequestId、
   key/hash 和 expectedRevision。
2. Widget 读取同一 canonical DB snapshot；Widget mutation 也只发 Agent command。两边

3. 每个变化恰好一个 revision；同一事务的多 Task/change 不拆 batch；no-op 不增 revision；
   event 丢失仍可 GET CHANGES SINCE 恢复。
4. 观察当前 Main/Widget Activation 只激活宿主，不接受 Task/SQL/key，不产生业务 response。

### C. 并发、幂等、timeout 和 cancel

1. 让 Main/Widget 从同一 R 发并发 create/result/reorder；验证 Agent 串行化、stale 无业务
   变化、reorder 多行一个事务/History/journal/revision。
2. 在 commit 前、commit 后分别丢 response/断 pipe；客户端只能显示 confirming/unknown，
   用 command.status、receipt、changes 或原 command 同 key/hash 对账。
3. 发送同 key/same hash 两次和同 key/different hash 一次；确认 replay 不重跑、
   conflict 不执行。
4. 注入 pre-commit cancel、post-commit cancel、pre-transaction timeout 和 Agent crash；
   观察 outcome matrix，不能生成第二 key 来掩盖未确认状态。

### D. changes、gap、snapshot 和读取失败

1. 分页获取 GET CHANGES SINCE，覆盖 after=current 空、after>current ahead、after=0、
   max 1/128、并发上界和同 revision batch 不拆。
2. 在隔离 fixture 制造 oldest gap 和 journal interior gap；客户端必须保留旧 model，转
   full read-only snapshot，不猜测缺行。
3. 让 snapshot 反序列化/应用中途失败，确认旧 model 和旧 LastSeen 保留；完整对应
   SnapshotRevision 成功后才 atomic swap。
4. Agent 暂停时只读 DB 若可用则标 stale；不可用则显示 unavailable；任何情况下不写。

### E. Agent restart、watchdog 和 safe mode

1. 正常停止/重启 Agent，确认新 agentInstanceId、hello、receipt、revision/History
   保留；旧连接 command 不被自动判定为成功。
2. 在隔离 profile 用专用 crash injection 触发最多 3 次 normal restart，观察 10 分钟
   window、1/2/5 秒 backoff、marker 原子更新和 safe mode；不对真实 DB 操作。
3. 分别验证 SAFE_HEALTHY 的核心 Task 写入和 SAFE_UNHEALTHY 的只读/不可用，且两者
   都无 Main/Widget direct fallback。
4. 验证用户显式 Resume normal mode 后 marker 清除条件；失败时 marker 不丢失。

### F. 单实例、Widget 和用户隔离

1. 同 profile 启动第二 Main，确认 activation 后退出；启动相同 WidgetInstanceId 的
   第二 Widget，确认 activation 后退出；启动不同 ID，确认并存且共享 Agent。
2. 以另一个 Windows user 尝试 business read/write/status/event 和 activation；business
   全部拒绝，control 例外不返回 Task/revision/receipt/path。
3. 检查 Local pipe/mutex、ACL、ProfileScope 和 canonical path；不能因猜名或 control
   权限获得业务事实。

### G. Single cutover 和旧 binary

1. 记录 P2-PRE-CUTOVER-LAST，停止全部旧进程；执行 additive migration/health gate。
2. 对 Main/Widget/Bootstrap 做第 15.3 精确静态扫描并保留匹配分类；只允许测试夹具
   出现 fake/direct path。
3. 启动 post Agent 和 clients，保存 runtime writer proof；停止 Agent 后再次尝试 client
   写入，确认只返回 unavailable/read-only、DB 无变化。
4. 尝试启动旧 P2 binary 到 post profile，必须被 version fence/启动器拒绝或立即停止
   写入；发现旧 binary 与 Agent 共存就停止 gate，不继续验收。

### H. P2 回归、范围和签字

1. 在隔离 profile 回归 P2 的 ANYTIME、TIME、RANGE、Quick Add、DONE、RANGE result、
   NEEDS REVIEW、改期、排序、PARTIAL continue、Parser error、History 和重启保留。
2. 检查 schema、pipe traffic、logs 和进程，确认无 ReminderRule/Schedule/Instance、
   Scheduler/Toast/Tray/Anime/Sync/network/E2EE/updater。
3. 自动测试、fake、CLI/harness、Codex/UIA、真实进程和用户正常桌面各自记录；用户
   只有在正常桌面实际操作后才签字。
4. P2 的真实 23:00 → 次日 00:30 → 01:00 仍须由用户另行完成；本 P2.5 验收稿不覆盖、
   不替代、不关闭该 Pending，不改系统时间。

## 20. 失败即停止条件

出现任一条件，当前 checkpoint 立即判失败，停止继续派发 production 或标记 runnable，
保留原数据和失败证据：

- 任一 runnable checkpoint 同时存在 Agent writer 与 Main/Widget/Bootstrap 合法业务 writer；
- Bootstrap 打开业务 DB、migration、DbContext、Task service 或 command；
- Main/Widget 有 writable handle、SaveChanges/Migrate/写 PRAGMA、P2 gate 或 direct fallback；
- 同 key/hash 产生重复 Task、Result、History、journal、receipt 或 revision；
- stale 被静默接受、reorder 半成功、timeout/cancel/断管道/Agent crash 造成半写或覆盖；
- receipt 缺少 outcome、CommittedRevision、key reuse 或 response loss 对账路径；
- RN-CJ-1 vector 不一致、重复 key/unknown field/非法数被执行、敏感 payload 出现在
  logs/event/error/receipt；
- frame/UTF-8/JSON/partial I/O/上限/byte order 不符合，或 in-flight/deadline 无界；
- 未 hello/错误 major/required feature 缺失仍能发业务命令；
- journal interior gap、ahead、after=0、整数边界未进入固定路径，或 LastSeen 虚推进；
- read model 应用失败清空旧列表、读取 revision 与 model 不对应、reader 改 schema/PRAGMA；
- 跨 user/profile 访问、pipe/control ACL 越权、错误泄露另一 profile 的事实；
- watchdog 无限重启、marker 非原子/越权、safe health failed 仍写，或 safe mode 恢复 direct；
- 第二 Main/同 ID Widget 未激活退出，不同 ID 不能按规则并存；
- migration/WAL/integrity failure 删除/覆盖/重建 DB，或旧 P2 binary 与 post Agent 共存；
- P2 Task/Today/Parser/History 语义回归、引入 Reminder/Anime/Sync/network；
- 把 fake、空库、CLI/UIA、Codex smoke、固定 Instant 或独立自动化写成用户签字；
- 试图用本文件覆盖 P2 真实跨午夜 Pending。
